## 执行顺序

1. 业务约束：预算/币种来源与口径、配送与多轮约束保持、目录品类映射、偏好冲突、
   候选数量与购买数量、商品/SKU/金额证据一致性、空结果/错误恢复。
2. 独立第二版数据：场景与实体分组隔离；覆盖正常调用、追问冲突、结果回答、失败恢复、
   多步保持。冻结测试不用于训练或模型选择。原 84 条只作为历史回归。
3. 本地 1.7B 显存试跑，优先 BF16 LoRA，必要时验证 QLoRA；按开发集选择 adapter。
4. 同条件基座/adapter 单步比较与完整 Agent 任务实跑；保留全部失败、校验质量和耗时。

## 数据与硬件选择

第二版 `eval/executor_v2` 已冻结：1,500 train / 200 dev / 300 test，
40 个完整任务。30 个共享业务家族，类别实体与主要表达按 split 隔离；属于合成任务，
不是 2,000 个独立真实用户场景。实际 tokenizer 最长 2,735 tokens，无截断。

8 条旧数据的 BF16 硬件试跑成功，但新样本更长，正式 BF16 运行显存缓存接近上限、
速度波动，因此在第一轮结束前停止该运行，保留 `aborted.json`。没有读取测试模型输出。
使用相同 40 条训练 / 4 条开发样本进行配置比较：

| 配置 | 总耗时 | 峰值 CUDA 分配 |
|---|---:|---:|
| BF16 LoRA，定期释放闲置缓存 | 195.80 秒 | 5,898,653,184 bytes |
| NF4 QLoRA，BF16 计算，定期释放闲置缓存 | 100.99 秒 | 4,729,324,032 bytes |

选择 QLoRA 仅基于上述硬件结果。40 条样本的 profile adapter 已完成保存、CPU 张量
完整性检查、BF16 基座重载与 4 条开发样本生成；不作为最终 adapter 或质量结论。

正式运行：`training/outputs/executor-v2-1.7b-qlora`，从原始固定基座重新开始，
seed 42，r=8，alpha=16，dropout=0.05，q/k/v/o 投影，学习率 1e-4，
2 epochs，梯度累积 8，最大长度 3,072，只监督最后 assistant 目标，按开发集 loss 选权重。

已启动顺序比较脚本 `training.run_comparison_v2`：等待训练进程完成后，核验冻结哈希与
adapter 完整性，再执行基座/adapter 各 300 次单步测试及各 40 个完整任务。
两组推理统一 BF16、greedy、最多生成 256 tokens；完整任务用固定派发器和合成商品库，
真实执行 MainAgent → fork → 本地模型 → 生产商品过滤工具。
原始选择错误与确定性业务校验后的成功分开统计。阶段写入
`eval/reports/executor-v2/comparison_status.json`，不切换应用默认模型。

正式 QLoRA 训练完成，耗时 7,003.30 秒（116.72 分钟），峰值 CUDA 分配 4.47 GiB。
开发 loss 从 1.791724 降至 epoch1 的 0.003344、epoch2 的 0.002049，选用 epoch2。
adapter 共 224 个张量，全部有限，112 个 LoRA B 均非零，完整性检查通过。
300 条严格单步测试：基座 94/300，adapter 248/300；中位生成耗时 1.87 → 3.22 秒。
计价不可用的关键词漏判、允许的准备动作与单步标注不匹配、实际澄清失败均保留并分别解释。
