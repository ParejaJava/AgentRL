# 八、评测、可观测性、可靠性、安全与性能

> 证据口径：本章必须引用正式 `TEST-001`、`ORCH-001`、`CTX-001`、`RAG-001`、`SEARCH-001`、`REL-001`、`OBS-001` 报告，不使用未测量的生产收益。

> 当前证据边界：正式 Offline 快照通过 170 项测试和 17 类故障注入，覆盖 67 条商品、100 条品类冻结集；Live E2E 的 12 场景 × 3 次为 36/36 通过；Live Context 的三模式 A/B/C 全部通过。两套 live 均回读 3/3 条 Langfuse 抽样 Trace，但尚无真实生产流量和完整轨迹人工标注集。数字统一引用 `TEST-001`、`REL-001`、`E2E-001`、`CTX-001` 和 `OBS-001`。

## 1. 如何评估一个 Agent 或大模型应用的整体效果？除准确率外还应关注哪些指标？

应分层而不是只看最终文本：

- 任务层：完成率、业务约束满足率、用户是否需要纠正。
- 决策层：路由、工具选择、参数、调用顺序、停止时机。
- 检索/生成层：Recall、MRR、NDCG、faithfulness、完整性。
- 系统层：首 Token/总延迟、Token/费用、工具错误率、重试/降级率、可用性。
- 安全层：越权、注入、秘密泄漏和高风险误操作率。

项目现有证据最强的是商品检索：67 条数据上 Recall@5=95.52%、Recall@10=96.27%、MRR@10=93.22%；这不能直接等同于端到端 Agent 成功率。后者还需轨迹和最终决策评测。

## 2. 如何评估 Tool Calling 的准确率？

把工具调用拆为：是否该调用、工具名、参数字段/值、顺序、调用次数、结果使用和最终停止。建立 gold trajectory 或允许路径集合，统计 tool selection precision/recall、argument exact/F1、sequence success、重复/非法调用率。

项目可构造场景：问品类常识应调用 `category_insight`；找商品用 `item_search`；无 `ship_to` 不要求到手价；创建订单前需搜索快照与明确确认；仅在三类条件下 fork。因为正确路径可能不唯一，评测应验证不变量和关键事件，而非要求完整消息逐字相等。

## 3. 没有显式用户反馈时，如何评估 Agent 效果？

使用隐式行为与代理指标：是否重复提问、任务是否中断/重试、工具是否成功、用户是否立即改写、结果点击/选择、订单意图是否继续、延迟与成本；再抽样人工评审或 LLM-as-Judge。代理指标会受 UI 和流量偏差影响，不能单独代表满意度。

本项目原型没有真实点击/转化数据，因此主要依赖离线 gold、领域不变量、事件轨迹和测试。面试中不能编造 GMV 或线上留存，可说明生产后会在用户授权下增加匿名漏斗和纠错信号。

## 4. 自动化评测与人工评测应如何结合？

自动评测覆盖量大、可回归，适合结构化参数、检索、规则、安全和性能；人工评测适合有用性、解释质量、细微事实和偏好匹配。LLM Judge 可做预筛，但要校准偏差，不能当唯一裁判。

流程可为：每次提交跑单测和小型 gold；发布前跑完整检索/轨迹集；高风险或自动分歧样本人工复核；人工结论再沉淀为回归用例。项目当前自动部分较强，端到端主观质量的人工 rubric 尚需补齐。

## 5. 如何建立 Agent 的自动评测体系和回归测试集？

先按需求树定义能力和失败分类，再为每类收集正常、边界、对抗和历史 bad case；数据包含输入、上下文、允许工具、期望状态/证据、不变量和预算。固定依赖快照和模型版本，输出机器可读报告，并在 CI 设置退化阈值。

项目已有两套冻结召回数据、pytest 和 12 个真实 Agent 场景；确定性控制流用 fake model 与故障注入测试，真实 Kimi 场景每条重复 3 次并保留失败样本。下一步应扩充人工标注的 trajectory 集，并按主/子 Agent、full/降级路径、语言、品类分桶，不能只追逐总平均分。

## 6. Agent 出现 Bad Case 时，如何快速定位问题？

先用 run/thread/session ID 找到 trace，然后沿链路看：输入与身份 → Prompt/Context projection → 模型 tool call → 参数校验 → 工具候选/结果 → 状态变更 → 最终回答。对比同版本正常样本，确定是数据、模型、编排、工具、上下文还是基础设施。

项目事件包含 run.started、agent.dispatch、tool.invoke/result、plan.update、context.compressed、cache.hit、budget.exhausted、drift/safety、token.delta、final.result 和结束/错误；LangFuse adapter 可关联主子 trace。大型结果在 D4 保留引用，可回放而不依赖模型当时的摘要。

## 7. 如何判断应该优化 Prompt、RAG、Agent 编排还是底层模型？

做最小替换实验：gold 证据未召回，优化数据/检索；gold 已进 Prompt 但答错，检查 Prompt/模型；调用了错误工具，检查工具描述/路由/训练；正确工具却顺序/依赖错误，优化编排与状态机；oracle Prompt 仍普遍失败，才考虑模型升级或微调。

项目将层次拆开后可分别评测。比如品类本地 Recall 低是检索问题，不应用加长主 Prompt掩盖；到手价错误应修领域规则；重复调用由 Harness 处理；复杂语义理解失败才可能是生成模型能力。

## 8. Agent 经常选择或调用错误工具时，如何排查？

查看工具是否名称/描述相似、Schema 太宽、候选过多、示例偏置、上下文含注入、工具结果错误导致下一步误判。统计混淆矩阵，并检查“本来不该调用”的 false positive。

改进顺序：收窄暴露工具；改互斥 docstring；强化参数类型与 enum；增加少量边界示例；前置路由；执行层权限与顺序校验；建立回归集。项目对子 Agent 工具白名单和订单 ToolHarness 就属于执行层兜底，不能只相信模型选对。

## 9. 如何设计 Agent 的日志、Trace 和可观测体系？需要记录哪些关键事件和指标？

日志用于离散事件，Trace 关联一次请求的父子 Span，Metrics 观察总体趋势。记录 run/thread/session/agent/tool、模型与 Prompt 版本、时间、状态、Token、缓存、重试、错误类型、候选数量、降级路径和安全决策；敏感输入要脱敏，API key 永不记录。

项目统一运行事件并接入 Langfuse，子 Agent 通过同一 trace context 形成父子拓扑。事件既供 SSE/WebSocket 用户进度，也供排障；持久事件和实时 Pub/Sub 要区分。正式 E2E 快照回读 3/3 条抽样 Trace，其中 2 条满足完整主/子拓扑；Context 快照回读 3/3 条，其中 1 条满足完整治理拓扑。公开报告只导出脱敏后的拓扑、Token 和延迟摘要；这证明接入可用，但不能声称全量遥测上传率为 100%（`OBS-001`）。

## 10. 如何监控 Agent 的运行状态？

建立状态机 queued/running/waiting_tool/waiting_user/succeeded/failed/cancelled，提供按 run 查询；指标监控活跃运行、队列长度/年龄、各阶段延迟、失败/重试/熔断/预算耗尽、worker heartbeat；对异常阈值告警。

项目 Redis Stream 有 job 状态、消费者组、重试与死信；TaskBoard 有任务状态；事件流给前端进度。生产化还需 Prometheus/Grafana、SLO、告警和分布式 worker 健康探针，当前仓库不代表这些已上线。

## 11. Agent 出现幻觉时，可以采用哪些工程缓解手段？

从来源、生成和验证三面处理：RAG/工具提供新鲜事实；Prompt 要求不确定时拒答和引用；结构化输出；领域函数计算数字；生成后做证据/规则校验；低置信度时追问或人工升级。高温度和强制回答应避免。

项目用 CategoryCard 原始证据、商品检索、到手价领域函数、订单参数核验和空结果降级。SafetyPolicy 处理注入/秘密，不能保证全部事实正确；后续需加 claim-evidence 支持率评测。

## 12. 如何保证 Agent 输出结果的可靠性和可验证性？

输出应区分事实、推断和建议；关键事实附来源/商品 ID/价格快照；结构化结果过 Schema；金额、状态和权限过确定性校验；保存输入、版本与 trace 以重放。对外部实时数据标记时间和可能变化。

项目商品卡包含平台、SKU、价格和可选到手价组成，CategoryCard 有 raw_evidence/confidence/更新时间，订单保存搜索快照并二次验证。支付未实现，所以不能向用户声称“已购买”。

## 13. 如何兼顾 Agent 系统的实时性和准确性？

采用分阶段结果：快速词法/缓存返回初步状态，向量与重排改善最终结果；独立工具并行；流式输出；按请求价值选择模型和检索深度；设置超时后降级。高风险写操作宁可慢一些也要复核。

项目 `category_insight` 有 quick/deep 语义，检索 full path 故障可降级，fork 并行独立任务，API 推送 token/事件。语义缓存只用于首轮、只读、上下文独立请求，写操作和指代型问题绕过，避免用错误缓存换速度。

## 14. Agent 线上响应越来越慢时，应从哪些方面排查？

先按 Span 分解：排队、模型 TTFT/生成、Prompt Token、每个工具、检索、重排、数据库、序列化和客户端传输。比较 P50/P95/P99 与历史、按模型/工具/降级/会话长度分桶。

常见原因是上下文增长、工具重试、并发限流排队、OpenSearch 慢查询、GPU OOM 后退 CPU、Redis/连接池、子 Agent 过度并发。项目可从 context.compressed、budget、retrieval_mode 和 tool RT 事件定位；没有生产指标时应通过负载测试复现。

## 15. 高并发场景下如何保证 Agent 服务稳定性？

入口限流与租户配额、模型/工具 bulkhead、全局和每用户 Semaphore、有界队列、超时、背压、熔断、缓存、降级、幂等和水平扩展。不能把所有请求无限创建协程，否则会把压力转移到模型、GPU 或数据库。

项目模型网关有全局并发和请求间隔；当前 Kimi 配额为并发 15、RPM 100、TPM 2,000,000，因此生产默认模型并发 12、子 Agent 并发 10，正式证据运行进一步固定为 10/8，并设置 0.75 秒启动间隔。任何更高吞吐结论仍必须经过压测。

## 16. 如何设计限流、熔断、降级和重试策略？

限流防止过载；熔断在连续失败时快速失败；降级选择较弱但可用路径；重试处理瞬时故障。顺序通常是超时与错误分类 → 有预算的退避重试 → 达阈值熔断 → 降级/返回明确错误。四者必须共享错误语义和观测。

项目模型网关有 Semaphore、最小间隔、瞬时重试和备用模型；工具有超时、本地/可选 Redis 熔断；检索有三级降级。缓存/共享熔断可 fail-open，但订单持久化不能。副作用操作只在具备幂等时重试。

## 17. 如何提升 Agent 的缓存命中率？

保持前缀字节级稳定：固定 System Prompt、工具顺序与 Schema、模型参数；将用户和动态状态放后缀；不要每轮重写摘要；按 Cache Epoch 只在纠正或结构变化时重建基线。同时对 Embedding、检索和安全的只读响应做正确键控。

项目以 L0 稳定前缀、L1 Epoch baseline、L2 动态 D2/D3/D1 组织 Prompt；Breakpoint 之前不压缩，之后按需增量压缩。语义缓存键包含 buyer 与偏好指纹，避免个性化串用。80% 命中率尚缺正式线上测量，应作为目标而非已证实结果。

## 18. 渐进式加载工具或 Skill 是否会导致 KV Cache 失效？

如果把新工具 Schema 插入已缓存前缀中间，插入点之后的 KV 都不能复用；若每轮工具集合/顺序变化，命中会很差。若稳定目录在前，具体按需内容只追加在断点后的动态区，则前缀仍可命中。

因此工具多时要固定候选排序、版本和序列化，按 Cache Epoch 更新。项目目前工具数量较少且固定装配；未来做 Skill 懒加载时，应让 ToolCatalog 摘要稳定，选中的详细 Skill 放 L2，而非重新拼装整个 System Prompt。

## 19. 性能测试通常关注哪些系统指标和业务指标？

系统指标：QPS、并发、P50/P95/P99、TTFT、tokens/s、CPU/GPU/显存、内存、网络、连接池、队列深度/年龄、错误/超时/重试/熔断。业务指标：任务成功、工具正确、召回质量、降级率、每成功任务 Token/成本和用户等待时间。

场景要覆盖冷/热缓存、短/长会话、单/多 Agent、正常/故障依赖、持续 soak 和突发流量。项目还没有完整性能报告，这是生产化前必须补齐的验收项。

## 20. QPS 和 TPS 有什么区别？CPU 利用率低但 Load 很高可能是什么原因？

QPS 通常是每秒请求数；TPS 是每秒完成的业务事务数，一个事务可能包含多次请求/模型和工具调用。Agent 场景还应看每秒 Token 和每任务调用数，仅看 QPS 容易误判容量。

Linux Load Average 反映可运行和不可中断睡眠任务数，不等同 CPU 利用率。CPU 低而 Load 高常见于磁盘/NFS I/O 阻塞、D 状态进程、锁/内核等待、容器配额或设备故障。应结合 `top`、`vmstat`、`iostat`、`pidstat` 和进程状态定位。

## 21. Linux 常用的线上排障命令有哪些？

按问题分类使用，不要无目标地贴命令：

- 主机：`uptime`、`top`/`htop`、`free -h`、`vmstat 1`、`mpstat -P ALL 1`。
- 进程：`ps aux`、`pidstat -p PID 1`、`pstree`、`lsof -p PID`、`strace -p PID`（谨慎）。
- 磁盘：`df -h`、`du -sh PATH`、`iostat -xz 1`、`iotop`。
- 网络：`ss -lntp`、`curl -v`、`dig`、`ping`、`traceroute`/`mtr`、`tcpdump`（需权限且注意敏感数据）。
- 日志/服务：`journalctl -u SERVICE --since ...`、`systemctl status SERVICE`、`dmesg -T`、`tail -f`、`rg`。
- 容器：`docker ps`、`docker logs`、`docker stats`、`docker inspect`、`docker compose ps`。

排障顺序是先确认时间、影响范围和变更，再看服务/依赖/资源，使用 run ID 关联应用 trace；执行重启、删除或抓包等有影响操作前需审批。项目在 Windows 开发，但 Docker 部署后这些命令适用于 Linux 宿主机。
