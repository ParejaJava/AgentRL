# 二、Agent 基础、架构与执行范式

> 证据口径：架构与执行结论引用 `ARCH-001`、`ORCH-001` 和 `REL-001`，状态以 [`../interview_evidence/README.md`](../interview_evidence/README.md) 为准。

> 回答口径：先回答通用原理，再落到本项目。当前项目是一个跨境购物 Agent 平台原型，采用 DDD-lite + 六边形架构，底层执行引擎是 LangChain `create_agent` 所构建的 LangGraph 图。没有实现的能力会明确标注。

## 1. 什么是 Agent？它与普通 Chatbot、Workflow 的本质区别是什么？

Agent 是“让模型在约束下持续观察状态、做决策并采取动作”的运行系统，不只是一次文本生成。它通常包含模型、工具、状态、循环、策略、记忆和安全边界。模型每轮可以回答，也可以生成工具调用；工具结果作为新观察回填，直到形成最终答案或触发终止条件。

- Chatbot 的核心是“输入消息，输出消息”，可能有历史，但不一定能行动。
- Workflow 的路径主要由开发者预先写死，例如 A 成功后执行 B，失败则走 C，确定性和可测试性强。
- Agent 的下一步由模型结合当前状态动态决定，适合路径难以穷举的问题，但成本、延迟和不确定性更高。

本项目采用混合方案：LangGraph AgentLoop 负责开放式理解和工具选择；订单确认、价格计算、任务依赖、权限校验等关键规则仍由确定性代码控制。也就是说，不把所有事情都交给模型。

## 2. 什么场景应该使用 Agent，什么场景不应该使用 Agent？

适合 Agent 的场景通常同时具备三个特点：目标明确但步骤不固定；需要读取多种信息或调用多个工具；中间结果会改变后续决策。例如“找适合雨季旅行的三件套，比较跨平台到手价，并按我的偏好解释取舍”。模型需要判断先查品类知识还是商品、是否补问目的地、是否并行拆任务。

不适合的场景包括：固定 CRUD、规则可以完整枚举、强实时低延迟、极高风险且不能容错的操作。比如支付扣款不能由 Agent 自主执行。本项目的订单能力只生成 purchase intent，必须显式确认 SKU、数量和目的地，也没有真实支付、库存锁定、退款能力。

判断原则是：能用普通函数或 Workflow 清晰表达，就优先使用确定性实现；只有“不确定的决策部分”才交给 Agent。

## 3. Agent 通常由哪些核心模块组成？如果从零设计一个 Agent，会如何组织这些模块？

核心模块包括：模型网关、Prompt、工具注册表、AgentLoop、状态与 Checkpoint、上下文治理、任务编排、权限与可靠性策略、事件流和评测体系。

本项目没有把这些都堆进一个 `agent.py`，而是按依赖方向组织：

1. `domain` 放商品、金额、运费、关税、订单和偏好等纯业务模型与规则。
2. `application` 放运行 Agent、派生子 Agent、执行任务等用例，以及模型、会话、队列等端口。
3. `infrastructure` 放 LangGraph、模型供应商、OpenSearch/FAISS、SQLite/Redis、LangFuse 等适配器。
4. `presentation` 放 FastAPI、SSE 和 WebSocket。
5. `composition.py` 是唯一装配根，把抽象与具体实现接起来。

这样领域规则可以脱离模型和检索框架单测，基础设施也可替换。

## 4. 如何设计一个可扩展的 Agent 框架？

扩展性不只是“工具可以继续加”，还包括模型、存储、编排和接入层可替换。设计时应做到：稳定领域模型、显式端口、单一装配根、声明式工具契约、统一运行事件、可组合中间件以及分层测试。

本项目的做法是：工具统一用 `@tool` 声明完整类型和 docstring；运行时依赖通过工具工厂闭包注入；应用层依赖协议而不是 OpenSearch、Redis 或 LangGraph 的具体类；模型限流、预算、上下文压缩、安全检查等以中间件或网关组合；事件统一映射为 `run.started`、`tool.invoke`、`token.delta`、`final.result` 等协议。

新增平台时只增加商品召回适配器，新增模型时只增加模型网关配置，新增接入方式时不改领域规则。真正需要注意的是接口版本、错误语义和可观测字段也必须稳定，否则只是把耦合从类移动到了 JSON。

## 5. Agent Loop 的内外双循环如何设计？内循环和外循环分别负责什么？

内循环是单次运行里的“模型—工具—观察”循环：调用模型，读取 `tool_calls`，执行工具，将 `ToolMessage` 回填，再调用模型，直到输出最终答案。这部分由 `create_agent` 编译出的 LangGraph 图执行。

外循环管理一次运行的生命周期：解析会话身份、恢复 Checkpoint、注入偏好与上下文、选择同步或队列执行、发布事件、记录 Trace、保存结果，并处理重试或恢复。本项目的 FastAPI/worker 和应用用例承担外循环，LangGraph 承担内循环。

区分两层很重要：模型调用失败可以由模型网关重试；整次任务失败是否重放则由外循环决定。否则一次工具副作用可能因错误重试而被重复执行。

## 6. ReAct 的完整循环和工程执行逻辑是什么？

ReAct 可概括为 Reason + Act，但工程里不是要求模型公开长篇思维链，而是让它反复执行：读取状态 → 选择回答或工具 → 校验调用 → 执行工具 → 写入观察 → 再决策。

在本项目中，用户消息进入主 Agent；模型可能先调用 `category_insight` 获取品类知识，再调用 `item_search` 搜商品，也可能用 Task 四工具形成任务 DAG，或在满足条件时调用 `fork_sub_agents`。每次工具调用都会经过参数 Schema、ToolHarness、安全/熔断/超时逻辑。返回值作为工具消息追加到图状态，下一轮模型据此继续。没有工具调用时，AIMessage 即最终答案。

循环的停止条件包括：模型给出最终答复、工具或安全策略返回不可继续的错误、预算不足、框架递归上限等。当前项目还有重复同参工具调用拦截，但尚未配置一个业务自定义的 `max_iters=15`，不能把简历设想当作已实现事实。

## 7. ReAct 中的消息格式应如何设计？Tool Response 应以什么角色传回，为什么？

常见消息包括 System、User/Human、Assistant/AI 和 Tool。模型生成的工具调用位于 AIMessage 的 `tool_calls`；工具执行结果必须用 ToolMessage 回填，并携带与调用一致的 `tool_call_id`。这样模型和框架才能把“调用请求”与“调用结果”正确配对，尤其是在并行调用时。

不能把工具结果伪装成 UserMessage：那会让模型以为结果来自用户，破坏角色语义，也可能绕过工具结果清洗和调用闭合检查。本项目的上下文治理还会把一个 AI 工具调用及其对应 ToolMessage 视为完整消息组，D1 热上下文保护时成组保留，避免裁剪出孤立调用。

## 8. ReAct 框架中的异步逻辑如何实现？

异步要贯穿调用链：模型使用 `ainvoke/astream`，I/O 工具用 `async def`，独立任务用 `asyncio.gather` 并发，并通过 Semaphore 控制总并发。同步 CPU/GPU 重任务不能直接堵塞事件循环，应放到线程池、进程、独立推理服务或 worker。

本项目的子 Agent 通过异步调用并行执行；模型网关有全局信号量和最小请求间隔；运行上下文通过 `ContextVar` 在协程任务中传播；长任务通过 Redis Stream 提交给 worker，API 通过事件流返回状态。并行不是无限制地 `gather`：还要保证任务依赖独立、工具无冲突，并让共享 Token 预算原子扣减。

## 9. ReAct、Chain of Thought、Plan-and-Execute 的核心区别是什么，如何选型？

Chain of Thought 是推理提示方式，本身不提供工具、状态和执行机制，而且生产系统通常只需要结果与可验证依据，不应依赖输出隐藏推理过程。ReAct 是边观察边行动，适合环境反馈频繁、下一步取决于工具结果的任务。Plan-and-Execute 先形成计划，再逐步执行，适合长链任务，但计划可能过早失效，需要重规划。

本项目是混合方式：短任务直接 ReAct；复杂任务用 TaskCreate/List/Update/Get 维护显式 DAG，再由主/子 Agent 执行。计划是结构化状态，不是模型输出的一段不可控文本；工具结果仍能推动后续调整。

## 10. Tree of Thoughts 是否适合线上系统？如何权衡成本和效果？

ToT 同时展开多条推理分支并打分，可能提高复杂搜索或规划任务的成功率，但会成倍放大 Token、延迟和状态数量。它不适合大多数低延迟线上请求，更适合高价值、可离线、分支空间有限且有可靠评价器的问题。

本项目没有实现 ToT。当前的 `fork_sub_agents` 是把可独立的真实子任务并行执行，不是对同一问题生成多条思维链竞争。如果将来引入，可只对高不确定、高价值的选品任务启用，设置分支宽度、深度、预算和早停，并用确定性指标而不是让同一个模型随意自评。

## 11. 单 Agent 与多 Agent 有什么区别？哪些场景需要多 Agent？

单 Agent 的工具和上下文集中，结构简单、延迟低、调试容易；但工具多、任务长时容易出现上下文污染、选择混淆和串行瓶颈。多 Agent 将任务、上下文和权限拆开，可并行、隔离错误，但增加编排、通信、一致性与成本问题。

需要多 Agent 的典型情况是：子任务可并行；需要上下文隔离；工具/权限集合明显不同；调用链很深。项目把这三项固化为 `should_fork` 判断：可并行、需要隔离、或调用深度达到 3 层，满足任一项即可派生子 Agent。

## 12. 为什么项目选择单 Agent 而不是多 Agent，或选择 Agent Teams 而不是 Workflow？

本项目并非纯单 Agent，也不是固定角色的“搜索 Agent/交易 Agent”团队，而是一个主 Agent 加按需派生的同构子 AgentLoop。原因是业务任务的能力集合相近，主要问题是上下文隔离和并行，而不是人格或专业身份不同。

子 Agent 复用主 Agent 已编排好的运行逻辑、状态 Schema、模型中间件和只读检索工具，但获得独立 `thread_id`、run 和会话目录。涉及偏好、订单、任务板写入的工具只留给主 Agent。与固定 Workflow 相比，它能处理用户开放式需求；与多个长期驻留角色相比，它减少重复 Prompt、图和状态模型。

## 13. Agent Teams 相比 Workflow 有哪些缺点？

主要缺点是：调用次数更多、延迟和费用更高；自然语言交接会丢信息；共享状态可能冲突；错误来源跨 Agent 扩散；执行路径更难复现；评测组合爆炸；权限面扩大。

因此项目只在三个条件之一满足时 fork，并且只回传子 Agent 最终答案，不把完整中间历史灌回主上下文。任务并行前还会检查 DAG 依赖和可运行状态。对订单状态机、到手价计算等确定性逻辑仍使用普通代码，不使用 Agent Teams。

## 14. 多 Agent 场景中如何划分子 Agent 的职责并分配任务？

应按能力边界、数据边界、风险边界和可并行性划分，而不是仅按“起几个名字”。任务描述需包含目标、输入、约束、输出格式、依赖和完成标准；父 Agent 只派发闭合任务，子 Agent 不应再猜父上下文。

当前项目的子 Agent 是同构执行单元，职责是只读的品类洞察和商品搜索。父 Agent 使用 Task DAG 表达依赖，再把互不依赖且状态为 runnable 的任务并发派发。偏好修改、订单意图、取消订单等高风险或会写状态的能力不下放，这构成明确权限边界。

## 15. 多个 Agent 如何协作、共享信息和通信？

协作信息应分三类：任务合同、必要上下文和执行结果。优先传结构化 DTO/任务状态，不共享整段聊天历史。进程内可通过函数调用和 `ContextVar` 传递只读会话快照；跨进程通过持久化任务队列、状态仓库和事件总线通信。

本项目中主 Agent 把任务描述传给子 Agent，每个子 Agent 使用独立线程和上下文；购物会话标识、可信 buyer 等通过运行上下文传播；结果写回 TaskBoard，并只将最终摘要交给主 Agent。Redis Stream 负责长任务派发，Pub/Sub + 本地 fan-out 负责用户进度事件，SQLite/Checkpoint 承担可恢复状态。

## 16. 主 Agent 如何获取子 Agent 的执行过程、对话进度和最终状态？

最终状态通过 `fork_sub_agents` 的结构化返回和 TaskBoard 的任务状态获得。子 Agent 会发出 `agent.dispatch`、工具调用/结果、完成或错误等运行事件，presentation 层可按会话路由到 SSE/WebSocket；LangFuse 回调可记录主/子运行的 trace 元数据。

需要区分“用户/运维可观察”与“进入主 Agent 上下文”：当前实现不会把子 Agent 的全部中间对话返回给主模型，而只返回最终内容，从而减少上下文污染。若主 Agent 要细粒度监督，应增加结构化阶段结果或 task event projection，而不是复制完整消息历史。

## 17. 子 Agent 执行长耗时工具任务时，适合采用什么通信方案？

不应让 HTTP 请求一直阻塞。较稳妥的方案是：提交任务后返回 `job_id`；持久化队列投递；worker 领取并幂等执行；状态存储记录 queued/running/succeeded/failed；事件总线实时推送进度；客户端也可轮询查询。

本项目具备 Redis Stream 队列、消费者组、重试/死信、任务状态和 WebSocket/SSE 事件通道。同一线程的普通任务与大任务可进入不同 Stream，worker 优先处理普通队列。Redis 故障时不能假装任务已提交；而纯缓存、共享熔断这类辅助能力则可 fail-open。

## 18. Workflow、Agent 与 Tools 在架构层面的本质区别是什么？如何设计 Workflow 与多 Agent 的分层架构？

Tool 是有契约的原子能力，负责“做一件事”；Workflow 是开发者规定的控制流，负责“按确定路径组合能力”；Agent 是模型驱动的决策器，负责“在允许范围内决定下一步”。三者不应混成同一个大函数。

推荐分层是：接口层接收请求；应用层管理运行和 Workflow；领域层提供规则；Agent 只负责不确定决策；Tool 作为应用能力的适配入口；基础设施层完成模型、数据库和外部 API。项目的主 Agent 可动态选择工具，Task DAG 提供半确定编排，订单状态机和到手价计算保持确定性，这就是混合分层。

## 19. Agent 如何避免死循环、无限循环或反复调用同一个工具？

至少需要五类保护：总轮次/递归上限；Token/费用/时间预算；相同工具同参数去重；无进展检测；工具熔断和终止错误。还可根据状态机限制工具顺序，并在连续空结果时要求改写查询或停止。

本项目已经有同参重复调用拦截、工具级超时与熔断、Token Budget、目标漂移/连续空结果检测、Task DAG 状态机和 LangGraph 自身递归限制。当前不足是没有把业务可配置的最大 Agent 轮次显式沉淀为统一配置项，面试时应如实说明这是待完善点。

## 20. 如何设计 Agent 的权限控制，约束高风险操作？

权限不能只写在 Prompt 里，要在工具暴露、应用服务和领域规则三层强制执行。原则包括最小权限、读写分离、身份由可信运行时注入、危险操作二次确认、参数白名单、审计和幂等。

本项目对子 Agent 只暴露 `item_search` 和 `category_insight`；偏好、订单和任务写工具只在主 Agent。`buyer_id` 等身份来自 `ContextVar`，不相信模型任意传入的 ID。订单只创建购买意图，要求明确 SKU、目的地、数量并做快照核验；尚未接入真实支付。因此 Prompt 是提示层，工具和领域校验才是安全边界。

## 21. 如果 Agent 决策错误导致数据误删等严重后果，系统设计上如何防范？

首先避免给模型直接数据库权限，而是提供窄接口；其次危险操作采用“计划—预览—确认—提交”两阶段；使用软删除、版本号、幂等键、事务、审计日志和可回滚补偿；目标范围必须由服务端重新解析和校验，不能直接执行模型生成的 SQL 或路径。

本项目当前没有真实支付或大范围删除。取消订单意图和删除偏好都通过领域服务执行，身份来自运行上下文。若未来接平台交易，应增加人工/策略审批、库存与价格二次校验、支付令牌隔离以及 outbox/saga 补偿，不能仅依赖 Agent 自我反思。

## 22. 在流程完全自动化、没有人工交付把关时，如何保证 Agent 的可靠性？

自动化不等于取消控制面。要把开放式生成限制在可验证边界中：输入/输出 Schema、领域不变量、策略引擎、工具白名单、超时重试、熔断降级、幂等、离线回归、灰度和全链路审计。对无法自动验证的高风险动作，应降低自治等级而不是勉强全自动。

本项目的搜索结果可自动用 Recall/MRR/NDCG 评测；价格由确定性 Money/运费/关税规则计算；写操作有确认和状态机；检索有三级降级；模型网关有限流与预算；错误和事件可追踪。真正支付仍不自动执行，这正是可靠性边界。

## 23. 如何在可控性与 Agent 能力之间取得平衡？

可采用“模型决定意图，代码决定权限；模型提出参数，Schema 和领域层验证；模型选择路径，预算和状态机限制边界”的原则。自治程度应随风险变化：搜索和总结允许较高自治，偏好写入需明确语义，订单与支付需要确认或审批。

项目里的主 Agent 能自主决定查知识、搜商品、拆任务或 fork；但可调用的工具集、子 Agent 权限、并发条件、订单状态和到手价算法都是确定的。这样保留自然语言任务处理能力，同时让关键业务结果可测试、可审计。

## 24. 当前阻碍 Agent 大规模落地的主要挑战是什么？

主要挑战包括：模型决策不可完全复现；长上下文成本和信息污染；工具与外部数据质量参差；延迟和并发成本；安全与权限；端到端评测困难；跨版本回归；缺少可靠的人机责任边界。

本项目分别通过四层上下文、工具契约、检索评测、网关限流、Task DAG、事件追踪和领域隔离缓解，但仍处于工程原型阶段。OpenSearch/Redis 已完成本地 Docker 与健康探针验证；正式 live 快照均从 Langfuse 回读 3/3 条抽样 Trace，E2E 中 2 条满足完整主/子拓扑，上下文中 1 条满足完整治理拓扑。这些是受控实验的 `verified` 证据，不等于真实生产容量、稳定性或大规模线上落地（`E2E-001`、`CTX-001`、`OBS-001`）。

## 25. Agent 的自进化或自我学习机制可以如何设计？

安全的自进化应是离线数据闭环，而不是让线上 Agent 随意修改自己。流程可以是：收集 trace 和失败样本 → 归因 → 人工/规则标注 → 更新评测集 → 优化 Prompt、路由、工具描述或检索 → 影子评测和灰度 → 达标后发布。模型训练则另行做 SFT/DPO/RL，并保留版本与回滚。

本项目已有事件、评测数据、漂移检测和检索报告，可形成上述闭环；但没有实现自动改 Prompt、在线训练或权重更新。因此面试时应说“具备自进化的数据基础和设计”，不能说已经自我学习。

## 26. Pi Agent、DeepSeek Harness 等不同 Agent 的设计哲学、差异与优势是什么？

Pi 的核心倾向是轻量、可扩展的 coding-agent harness：基础能力保持少而稳定，通过扩展、skills、项目上下文和工具组合增加能力；其子 Agent 示例使用独立进程获得上下文隔离，可单个、并行或链式执行。它适合研究最小 AgentLoop 与可扩展外壳之间的边界。参考：[Pi monorepo](https://github.com/badlogic/pi-mono)、[Pi system prompt](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/system-prompt.ts)、[Pi subagent example](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts)。

DeepSeek Harness 强调“everything is a plugin”和可替换运行部件；Agent 接口、事件和注册机制尽量不绑定某一个循环实现，并将持久 session/event 与活跃 Agent 状态分开。优势是内核边界清晰、插件化程度高，代价是平台抽象和治理复杂度更大。参考：[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)、[Agent package](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent/README.md)、[Agent lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/agent-lifecycle.md)。

本项目没有复制二者：它使用 DDD-lite + Hexagonal 保护购物规则，以 LangGraph 做可恢复执行，以应用端口隔离具体框架。相同点是重视 harness、上下文和扩展边界；差异是本项目围绕电商决策而不是通用编程终端。

## 27. To-Do List 机制为什么能让模型更聚焦？如何在 Agent 中落地并更新任务状态？

To-Do List 把隐含计划外化为有限的结构化状态，降低模型每轮重新理解目标的负担，也便于检查遗漏、依赖和进度。字段至少包括 task_id、描述、依赖、状态、结果、版本和错误；状态迁移应由工具校验，不能让模型随意覆写整个列表。

本项目实现了 TaskCreate、TaskGet、TaskList、TaskUpdate 四工具和 SQLite TaskBoard。它支持 DAG 依赖、环检测、乐观并发重试、原子 claim 和结果写回。只有依赖完成的 runnable 任务可执行；并行选中的任务还必须彼此独立。这样“可并行”路由条件可以与任务工具联动，而不只是 Prompt 中的一句描述。

## 28. 用户需求信息不足或表达模糊时，Agent 如何判断直接回答还是追问澄清？

关键看缺失信息是否会显著改变结果、是否涉及不可逆动作、是否可从安全默认值或上下文可靠推断。低风险、可撤销的信息缺失可使用明确默认值并说明；目的地、SKU、数量、预算上限等影响价格或交易的硬约束则必须追问。

项目中商品搜索参数由结构化 Schema 校验；`ship_to` 缺失时仍可返回商品，但不内联到手价；创建订单意图时若 SKU、数量或目的地不完整则不能猜。长期偏好可用于排序，但不能代替本轮用户的明确约束。实践上还应让追问一次只聚焦最关键缺口，避免把用户变成填表者。
