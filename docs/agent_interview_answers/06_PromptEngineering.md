# 六、Prompt Engineering

> 证据口径：系统提示、工具描述和稳定前缀设计分别引用 `ARCH-001`、`CTX-001`、`REL-001`。

> 当前项目的主/子 Agent Prompt 是版本库中的 Python 常量，依靠工具 docstring、Schema 和运行时策略共同约束。尚未实现独立 Prompt Registry、在线 A/B 或自动 Prompt 优化。

## 1. 什么是 Prompt Engineering？

Prompt Engineering 是设计模型输入，使它理解角色、目标、上下文、约束、可用动作和输出契约的工程过程。它不仅是“措辞技巧”，还涉及消息角色、信息顺序、工具描述、示例、结构化输出、上下文选择和版本评测。

在 Agent 中 Prompt 只是一层软约束。项目用 Prompt 告诉模型何时搜索、何时查品类知识、何时 fork 和订单边界；真正的参数、权限、幂等和业务不变量由 Schema、Harness 与领域层执行。

## 2. 一个高质量 Prompt 或 Prompt 模板应包含哪些核心信息？

通常包括：角色与目标、已知上下文、任务边界、可用工具及选择标准、关键约束、缺失信息处理、输出格式、成功标准和少量高价值示例。还应明确冲突优先级：系统/安全规则、本轮用户明确要求、历史偏好、默认值。

好的 Prompt 应短、无自相矛盾、可测试。把所有业务文档和异常处理都堆进去会降低可维护性；可机器校验的规则应移到代码。

## 3. System Prompt 与 User Prompt 有什么区别？

System Prompt 由应用控制，定义 Agent 身份、全局能力和不可越过的行为边界；User Prompt 表达本次任务和偏好。二者冲突时系统级规则优先，但系统提示仍可能受注入影响，不能代替权限控制。

项目的 `MAIN_SYSTEM_PROMPT` 说明购物助理职责、工具使用、任务拆解、fork 和订单确认；`SUB_AGENT_SYSTEM_PROMPT` 限定子循环只做只读检索。用户消息保持原始需求，可信 buyer/session 不由用户 Prompt 提供，而由运行上下文注入。

## 4. Zero-shot、Few-shot 与 Chain of Thought 分别是什么，如何选择？

Zero-shot 只给任务和规则，成本低；Few-shot 给少量输入输出/工具选择示例，适合边界易混淆或格式不稳定；CoT 引导分步推理，适合复杂问题，但不应要求生产模型公开冗长隐藏思维链，可改为输出简短计划、证据和结论。

本项目主要靠 Zero-shot 规则、工具 Schema 和结构化状态。若 `category_insight` 与 `item_search` 经常混淆，可增加覆盖“问品类常识/找具体商品/先知识后搜索”的少量示例，并用工具选择回归集验证，而不是无上限增加推理文字。

## 5. 提示词工程常用的关键技巧和优化方法有哪些？

包括任务分解、明确正反边界、结构化输出、few-shot、检索增强、把变量放清晰分隔区、要求引用、提供失败策略、减少歧义、固定稳定前缀和按需加载上下文。对于 Agent，还要优化工具名、docstring、参数描述与工具间互斥性。

安全上应把外部文本标记为数据而非指令，并对工具结果清洗。效果优化必须配合温度、模型版本和评测集固定，否则无法知道提升来自哪里。

## 6. 项目中的 Prompt 是如何设计和迭代优化的？

设计从真实工作流反推：主 Agent 可以直接搜索，也可查品类知识、管理 Task DAG、按三条件 fork；订单只生成意图且必须确认硬参数。子 Agent 使用更窄 Prompt 与只读工具，避免继承主 Agent 的写权限。工具的详细“何时用”主要落在 docstring，减少主 Prompt 重复。

迭代依据应来自 trace/bad case：选错工具就调整互斥描述；缺少参数则改追问规则和 Schema；重复调用由 Harness 拦截，而不是继续加警告。目前 Prompt 仍是代码常量，没有独立版本 ID 和系统化 A/B，这是可继续改进处。

## 7. 如何评估 Prompt 的好坏以及一次 Prompt 优化是否有效？

先定义任务集和分层指标：最终成功率、工具选择/参数准确率、轨迹长度、违规率、幻觉、Token、延迟。固定模型、采样参数、工具和数据，多次运行处理随机性；与旧 Prompt 做配对对比，并按意图分桶。

项目当前已有检索评测和代码测试，但 Prompt/Agent 轨迹 gold set 还不完整。应从真实场景构建“是否应查知识、是否应 fork、是否应追问、订单能否提交”等样例，检查事件序列和最终状态。不能用单个聊天案例判断优化成功。

## 8. 为什么 Prompt 优化会出现“修好一个 Case、破坏另一个 Case”的现象？如何避免？

模型行为是多约束共同作用，新增一句强规则可能覆盖另一意图；示例可能让模型过拟合表面词；Prompt 变长也会改变注意力与工具选择。局部手改没有回归集时最容易发生这种情况。

避免方法是：把问题归因到 Prompt/数据/Schema/编排的正确层；使用互斥且可泛化规则；维护正例、反例和边界集；每次变更跑全量；版本化并可回滚。能由代码解决的参数与权限问题不应靠 Prompt 打补丁。

## 9. Prompt 调优到瓶颈后，如何继续提升效果？

依次检查上下文质量、工具契约、检索、任务分解、模型能力和评测标签。可以增加结构化状态、reranker、专用小模型路由、模型升级或 SFT；也可减少任务难度，把计算和规则移到确定性服务。

项目提升路径主要不是继续拉长 Prompt：品类知识做 RAG；商品做混合召回与重排；任务依赖放 TaskBoard；到手价放领域函数；失败由网关和 Harness 管理。这样改进可测试，也减少模型负担。

## 10. Prompt 优化与 SFT 训练应如何选择？

Prompt 适合快速变化、数据少、需要透明规则的场景，成本低且易回滚；SFT 适合任务模式稳定、有高质量示范数据、Prompt 已难以稳定约束的情况。SFT 之前必须先确认问题不是检索、工具或标签错误，并评估训练/部署成本。

当前项目没有 SFT，使用通用 Kimi 兼容模型和工程约束是合理阶段。未来若积累大量高质量工具轨迹，可针对工具选择或结构化输出做 SFT，但安全与业务不变量仍必须留在代码，训练不能替代验证。
