# 三、Tool Calling、MCP、A2A、Skill、CLI 与 Harness

> 证据口径：工具权限、参数校验和 Harness 结论引用 `ARCH-001`、`COMMERCE-001`、`REL-001`。

> 项目边界：当前项目实现了 LangChain Tool Calling、Task 工具、可靠性 Harness、队列和事件协议；没有接入 MCP、A2A，也没有实现可安装的 Skill 系统。相关问题以下按“原理 + 若接入本项目的方式”回答。

## 1. 什么是 Function Calling 或 Tool Calling？从模型生成调用意图到工具结果回填，完整流程是什么？

Tool Calling 是模型输出结构化调用意图、宿主程序真正执行函数的机制。流程是：应用把工具名称、描述和 JSON Schema 交给模型；模型返回工具名、参数和 `tool_call_id`；运行时校验参数与权限；执行本地函数或远程 API；将结果以匹配该 ID 的 ToolMessage 回填；模型根据观察继续调用或生成最终答案。

模型从不直接执行 Python。本项目的工具均用 `@tool` 声明，类型注解形成参数 Schema，docstring 告诉模型何时使用；运行依赖通过 factory closure 注入。`create_agent` 负责 AIMessage—ToolMessage 循环，ToolHarness、领域服务和中间件负责执行边界。

## 2. 模型为什么不能直接操作数据库或外部系统？

模型本质上只做 Token 概率预测，没有数据库连接、凭据和操作系统权限。即便把凭据交给模型也不安全：它可能幻觉 SQL、被 Prompt Injection 诱导、越权或泄露秘密。

正确做法是由宿主程序提供最小权限工具：参数白名单、身份从可信上下文注入、服务端鉴权、事务和审计。项目中的偏好与订单工具调用应用服务，模型看不到 SQLite 连接；商品检索工具也只接收 ProductSearchSpec，而不是任意 OpenSearch DSL。

## 3. 一个 Agent 需要调用多个工具时，整体流程如何设计？

先区分依赖关系：有依赖的顺序执行，无依赖且无共享写冲突的才并行。每次调用都经过 Schema 校验、权限、超时和观测；结果进入状态后再决定下一步。长任务应转换成 job，而不是阻塞循环。

本项目既支持模型逐步调用 `category_insight → item_search`，也支持 Task 四工具建立 DAG。ToolHarness 对订单链路执行顺序约束；`fork_sub_agents` 只并行 runnable 且彼此独立的任务；每个子循环有独立上下文。

## 4. 如何保证工具调用参数正确？

需要四层校验：类型 Schema 保证形状；Pydantic/领域值对象保证范围与格式；应用层补齐可信身份并校验权限；执行前基于最新数据验证业务前置条件。错误要返回可行动、可区分的错误码，不要只抛模糊异常。

例如 `item_search` 使用结构化搜索规格校验 category、budget、currency、ship_to、top_k；Money 阻止非法金额/币种；订单意图核验商品、SKU、数量、目的地和搜索快照。`@tool` 的 docstring 提高模型选参概率，但不是安全保证。

## 5. 工具或 API 调用超时、报错或返回异常时，Agent 应如何重试、降级、补偿或恢复？

先分类：瞬时网络错误可指数退避加抖动重试；参数/权限错误不可重试；有副作用调用必须有幂等键；部分完成需要事务、Saga 或补偿；连续失败触发熔断；可替代能力走降级。

项目的 ToolResilience 提供工具级超时、本地熔断和重复调用阻止，可选 Redis 共享熔断；模型网关对瞬时错误重试并可切备用模型。两套检索均有三级降级。订单写入依靠幂等与领域状态机，不能用“让模型再试一次”代替补偿设计。

## 6. 是否应让大模型参与异常处理或自动恢复？适用边界是什么？

模型适合解释语义错误、改写查询、根据明确候选方案选择替代路径；不适合判断事务是否提交、盲目重试扣款、修改权限或吞掉系统错误。基础设施错误必须由确定性代码分类。

项目中空召回可让 Agent 改写关键词，工具返回的参数错误可引导模型修正；超时、熔断、重试次数、幂等和降级链由代码执行。高风险失败应停止并告知用户，而不是让模型“自愈”到不可审计。

## 7. 并行 Tool Calling 时如何保证数据一致性？

先只并行只读或互不相交的写操作；写操作使用事务、乐观锁/版本号、幂等键、唯一约束和原子状态迁移；汇总结果时保留 task/call ID，不依赖完成顺序。共享预算等计数器需锁或原子操作。

项目 TaskBoard 在 SQLite 中做原子 claim、乐观并发重试和 DAG 状态校验；并行任务必须无相互依赖。子 Agent 的 thread、run 和目录隔离；共享 Token Budget 在 ContextVar 传播的预算对象中协调。订单类写工具不下放给并行子 Agent。

## 8. 如何从代码耦合和安全边界角度设计工具隔离？

工具应是应用用例的薄适配器，而不是把数据库、Prompt 和业务规则揉在函数里。接口只暴露任务所需参数；依赖由工厂注入；领域对象负责不变量；具体存储实现位于基础设施层；不同 Agent 使用不同白名单。

本项目子 Agent 只有两个只读检索工具，主 Agent 才拥有任务、偏好和订单写工具。这样即使子模型被注入，也没有相应能力。替换 OpenSearch 或 SQLite 时，工具契约与领域逻辑不需要一起改。

## 9. 如何隔离不同业务会话中的工具和状态？

每次运行都要有不可混淆的 session/thread/run 标识，状态存储按租户和会话命名空间分区；工具不能从模块级可变全局读取“当前用户”。异步任务要显式传播请求上下文，完成后正确 reset。

项目使用 `shopping_session_id` 标识业务会话，LangGraph 使用 `thread_id` 做 checkpoint 命名，fork 生成独立 `sub-*` 线程。可信 buyer、会话上下文通过 ContextVar 注入；事件按会话路由；文件 artifact 进入独立会话目录。

## 10. 多个会话共用同一个全局变量会有哪些隐患？

并发请求会互相覆盖用户 ID、预算、目的地或 trace，导致串话、越权、错误扣减和难以复现的竞态；多 worker 下普通全局变量还根本不共享，表现会不一致。

不可变的模型客户端或连接池可以全局复用，可变的请求状态不可以。项目用 ContextVar 保存协程局部运行上下文，用数据库/Redis 保存跨进程共享状态，模型网关只把并发信号量等进程级资源作为共享对象。

## 11. 直接把 Session ID 传入内部工具会带来哪些问题？工具完全不感知会话是否可行？

让模型填写 Session ID 会暴露内部标识，并可能跨会话读取或写入；每个工具重复参数也污染 Schema。完全无会话意识又无法做偏好、审计和状态关联。

折中是“模型不可控、工具实现可感知”：presentation/application 层认证后将 session/buyer 写入 ContextVar，工具工厂从可信运行时读取，而不把它放进模型可生成参数。项目正采用这种方式。

## 12. 带状态的工具如何保证只执行一次或实现幂等？

为逻辑动作生成稳定 idempotency key，在数据库建立唯一约束；先查执行记录，再在事务中写状态与 outbox；重试返回原结果而不是重复副作用。状态迁移还应校验 expected version。

项目的订单意图和队列任务带稳定标识，Redis Stream 消费有状态、重试和死信，TaskBoard 原子 claim 防止同一任务被多个 worker 同时执行。真实支付尚未实现；若接入必须使用支付平台幂等键和对账，而不能只依赖进程锁。

## 13. 工具任务需要运行很长时间时，如何设计异步执行、状态查询和结果回传？

采用 Submit—Track—Notify：API 创建 job 并持久化后立即返回；队列交给 worker；状态机记录 queued/running/succeeded/failed/cancelled；客户端用查询接口或 SSE/WebSocket 获取增量；结果过大存 artifact，只返回引用。

项目使用 Redis Stream、消费者组、重试/死信和状态存储，事件总线把进度按 shopping session 推送。重连时客户端应先查持久状态，再续接实时事件，避免把 Pub/Sub 当作可靠历史日志。

## 14. 工具返回体量巨大的 JSON 时，会有哪些限制，如何避免挤占上下文？

问题包括 Token 成本、模型注意力稀释、上下文溢出、缓存前缀变化、序列化延迟和敏感字段泄漏。处理方式是字段投影、分页/Top-K、确定性截断、结构化摘要、原文落对象存储并返回 artifact URI。

项目的 L0 工具侧防线会清洗和限长返回；大型内容进入 D4 artifact，不直接注入消息历史；D1 只保留当前决策必要结果。需要追溯时通过引用读取，而不是把整份原文常驻 Prompt。

## 15. 工具库有上百个工具时，如何提高检索效率和工具选择准确率，并减少上下文占用？

不能每轮把全部 Schema 塞给模型。可按领域建立工具目录，先做意图/能力检索，再只加载候选工具；使用分层路由、命名空间、少量互斥描述和权限过滤；高频工具常驻，长尾工具按需加载。

当前项目主 Agent 只有 12 个常驻工具（配置 Tavily 时多一个 web search），尚未到必须做工具向量检索的规模。扩展到百级后应在 composition 前增加 ToolCatalog/ToolSelector 端口，同时保持稳定前缀，避免每轮候选顺序变化破坏缓存。

## 16. 两个 Tool 或 Skill 描述相似、导致模型选错时，如何排查和优化？

先从 trace 统计混淆矩阵，检查名称、docstring、参数和返回是否重叠。改进包括：使用动作+对象命名；明确“何时用/何时不用”；合并真正同质工具；增加路由器；提供边界 few-shot；用回归集验证，不能只修一个 case。

项目区分 `category_insight`（品类常识卡）与 `item_search`（具体商品），Prompt 明确前者可用于检索前收敛词，也可在检索后补充选购知识。若混淆，应按“用户要品类知识还是商品实例”建立工具选择评测。

## 17. 什么是 MCP？它解决了什么问题？

MCP 是模型应用与外部能力之间的标准化客户端—服务器协议，统一暴露 tools、resources、prompts 等能力，以及发现、调用和生命周期交互。它解决每个 Agent 框架都为每个数据源写私有适配的问题，但不自动解决授权、业务幂等和工具质量。

当前项目没有 MCP；工具是进程内 LangChain Tool。若接入，可将商品目录或企业知识服务做 MCP Server，在基础设施层实现 MCP Client adapter，再映射为应用端口，领域层不依赖 MCP。

## 18. MCP Server 和 MCP Client 分别承担什么职责？

Server 声明并执行 tools、提供 resources/prompts，校验输入、鉴权、限流和返回结果；Client 建立连接并初始化能力，发现清单，把 Schema 提供给宿主模型，发起调用并处理通知/错误。宿主 Agent 才负责决定是否调用。

因此 MCP Server 不是“大模型”，MCP Client 也不等同于 Agent。安全上 Client 仍须根据当前用户过滤可见能力，Server 仍须独立鉴权，不能认为调用来自 Agent 就可信。

## 19. MCP 底层使用什么传输协议和通信机制？

当前规范以 JSON-RPC 消息为核心，标准传输包括本地 `stdio` 和远程 Streamable HTTP；后者可使用 HTTP GET/POST，并可通过 SSE 流式发送消息。旧版 HTTP+SSE 已由 Streamable HTTP 替代。远程服务需校验 Origin、认证并安全管理 session。参考：[MCP Transports](https://modelcontextprotocol.io/specification/draft/basic/transports)。

传输只是载体，MCP 还规定初始化、能力协商、请求/响应/通知以及资源和工具语义。不能简单说“MCP 就是 SSE”。

## 20. MCP 与 Function Calling 有什么区别？

Function Calling 是模型输出一个符合 Schema 的调用意图；MCP 是应用与外部能力提供方之间的标准协议。二者可叠加：MCP Client 发现工具 → 宿主把工具 Schema 给模型 → 模型 Function Calling → Client 经 MCP 调 Server → 结果回填模型。

本项目目前只有前者：LangChain 工具 Schema + 本地执行。引入 MCP 的价值主要在跨进程、跨团队复用，而不是提升模型本身的选工具能力。

## 21. 什么是 A2A 协议？Function Calling、MCP 与 A2A 应如何选型？

A2A 标准化独立 Agent 间的发现、消息、任务生命周期、状态与 artifact 交换，适合远程、异构、可能长时间运行的 Agent 协作。最新官方规范支持 Agent Card 和多种绑定，强调任务与消息语义。参考：[A2A Protocol](https://a2a-protocol.org/v1.0.0/)。

- 调一个原子函数：Function Calling。
- 接入标准化工具或数据源：MCP。
- 委派给能自主规划、有自己状态的远程 Agent：A2A。

项目子 Agent 是同一进程/代码库里的 LangGraph 调用，无需 A2A；未来若把不同国家站点代理拆成独立服务，才值得用 A2A。

## 22. CLI 与 MCP 有什么区别？如何选型？

CLI 是面向进程/人的命令行接口，输入输出往往是文本、退出码和文件；生态成熟、容易复用，但 Schema、流式语义、权限和错误结构不统一。MCP 是面向 Agent 集成的结构化协议，支持能力发现与会话交互。

已有可靠 CLI 且只在受控机器运行时，可先包装成工具；跨机器、需多客户端发现或细粒度权限时适合 MCP。执行 CLI 必须使用参数数组、固定可执行文件、超时和沙箱，不能把模型文本拼接进 shell。

## 23. MCP 网关与传统后端网关有什么区别？设计时需要额外关注哪些问题？

传统网关关注 HTTP API 路由、鉴权、限流和负载均衡；MCP 网关还要理解能力清单、工具调用、resource URI、Prompt、会话、流式通知和模型可见 Schema。它需要按用户动态裁剪工具、检测 Prompt Injection、限制返回 Token，并做调用审计。

仍要复用传统网关能力：TLS、OAuth、WAF、配额、租户隔离。MCP 网关不能成为绕过后端授权的万能代理。

## 24. 如何理解 MCP、Skill 与 CLI 各自的作用和边界？

CLI 是可执行入口；MCP 是跨进程发现和调用能力的协议；Skill 是给 Agent 的可复用工作方法，通常包含说明、选择规则、模板和辅助脚本。Skill 可以调用 CLI，也可以指导 Agent 使用 MCP 工具，但三者不是替代关系。

简化理解：Tool/CLI/MCP 解决“能做什么和怎么执行”，Skill 更偏“什么时候做、按什么步骤做、如何验收”。当前项目有工具与 Harness 文档，没有完整 Skill 运行时。

## 25. Skill 的本质是什么？它与普通工具调用、Agent 分别有什么区别？

Skill 是可按需加载的操作知识包，让通用 Agent 在某一任务上遵循稳定流程。它可以包含 SKILL.md、示例、脚本、模板和验收规则。工具是原子执行能力；Agent 是做决策和循环的主体；Skill 不必是独立 Agent，也不一定提供新外部权限。

例如“商品召回评测 Skill”可指导 Agent检查数据、启动依赖、运行脚本、解析四个指标并禁止伪造最终结果；真正执行的仍是 CLI/工具。

## 26. Skill 的底层机制和懒加载机制如何实现？

启动时只索引 Skill 的名称、简介、触发条件和入口，模型先看到小型目录；命中后再读取完整说明和必要资源；执行过程仍受工具权限控制。可用关键词/Embedding/分类器召回，再做权限和版本过滤。

要防止懒加载破坏缓存：稳定目录放在缓存断点前，具体 Skill 内容放动态后缀；固定排序和版本；不用时不注入。项目若实现，可在应用层定义 SkillCatalog 端口，在文件或远程仓库适配器中加载。

## 27. 如何设计、编写和评估一个 Skill？

先写清触发条件、非适用场景、输入、依赖、步骤、危险动作、失败恢复和完成标准；把易错机械步骤放脚本，把判断留给 Agent；示例覆盖正常、边界和反例。评估应包含触发准确率、任务成功率、步骤遵循率、工具错误率、成本和延迟，并与无 Skill 基线对比。

Skill 必须版本化和回归测试。若只写一篇很长教程、没有触发边界和可验证输出，它不是可靠的工程 Skill。

## 28. `AGENTS.md` 与 Skill 文件有什么区别？

`AGENTS.md` 是仓库或目录范围内的长期协作约束，例如编码规范、测试命令和禁止事项，进入该范围的任务都应遵守。Skill 是某类任务按需启用的专门流程与资源。

本仓库 `AGENTS.md` 规定所有 LangChain 工具必须用 `@tool`、完整类型和 docstring，并在需要运行依赖时使用工厂闭包。这不是一个具体业务工具，而是所有相关代码修改都必须满足的项目规则。

## 29. 如果让你设计一个生成 PPT 的 Skill，会如何设计？

输入包括受众、目的、时长、品牌模板、语言和材料；流程为材料盘点 → 叙事大纲 → 页面结构 → 生成/复用视觉资产 → 构建 PPTX → 渲染每页 → 检查溢出、字体、对齐和事实 → 修订 → 输出源文件与 PDF。危险边界是版权图片、敏感数据和未经确认的外部发布。

评测维度包括信息覆盖、故事线、视觉一致性、可读性、引用准确、渲染错误数和人工评分。Skill 应附带模板、渲染脚本和 QA checklist，而不只是一段“帮我做 PPT”的 Prompt。

## 30. 什么是 Agent Harness？它通常包含哪些能力，在 Agent 中如何实现？

Harness 是包围模型和 AgentLoop 的工程控制面：工具执行器、权限、状态、上下文、重试、超时、熔断、预算、事件、沙箱、Checkpoint、观测与评测。模型决定行动，Harness 决定行动能否安全可靠地落地。

本项目的 Harness 分散在模型网关、ToolResilience、ToolHarness、上下文中间件、安全策略、TaskBoard、事件总线、队列、LangGraph checkpointer 与 LangFuse adapter 中。

## 31. Harness 工程如何应用到实际项目？

应从真实失败模式倒推：模型反复调用就加去重和轮次预算；工具大结果就 artifact 化；上游故障就超时/熔断/降级；副作用重复就幂等；难排查就统一事件和 trace。每项保护都要有测试和可观测信号。

本项目把商品搜索到订单意图、查询到取消等顺序规则写入 ToolHarness；检索模型故障自动降级；上下文溢出时保留 D1/D2/最小 D3 后重试；安全策略阻断注入并脱敏输出。这些比让 Prompt 写“请不要出错”更可靠。

## 32. 如何理解 Spec Coding 与 Harness 的关系？

Spec Coding 先把目标、接口、不变量、错误和验收标准写清；Harness 把这些规范转化为运行时约束和测试。Spec 是“应该怎样”，Harness 是“怎样强制并证明”。

项目中的 ProductSearchSpec、Pydantic 输出、任务状态机、订单不变量和事件 Schema 都是可执行规范；ToolHarness、领域服务和测试负责执行。没有可机器验证的 Spec，Harness 只能做通用重试，无法判断业务正确性。

## 33. Harness 为什么可能提升 Agent 的任务完成能力？

它减少模型必须自行记住的工程细节：自动提供正确上下文、阻止非法路径、恢复瞬时失败、裁剪噪声、保存进度并给出结构化错误。等价于缩小搜索空间，使模型把能力用于语义判断。

但 Harness 不能弥补错误数据和不合适的模型；过度约束也会阻断合法路径。因此需要用任务成功率、错误类型和成本做对照评测，而不是只统计“保护规则数量”。

## 34. Harness 工程中如何设计可扩展的测试框架？

按层测试：领域单测验证金额、关税、订单状态；工具契约测试验证 Schema 和错误；适配器契约测试保证 SQLite/Redis/OpenSearch 实现同一端口；图/用例测试使用 fake model 重放固定 tool calls；端到端测试覆盖事件顺序；故障注入覆盖超时、断网、重复消息和上下文溢出。

数据驱动回归集应固定输入、期望工具轨迹或结果、不变量和成本上限。项目最终代码有 170 项测试、两套召回评测、30 轮确定性编排实验和 12 个真实 Kimi 场景；仍应补充长时间并发 soak test 与更多模型版本回归，形成金字塔而不是全部依赖在线 LLM。数字引用 `TEST-001`、`ORCH-001` 和 `E2E-001`，不能从工作区口头统计直接进入简历。
