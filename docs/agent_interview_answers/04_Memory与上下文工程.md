# 四、Memory 与上下文工程

> 证据口径：会话治理引用 `CTX-001`，个性化偏好引用 `COMMERCE-001`；供应商无缓存 Token 明细时不得把稳定前缀率称为缓存命中率。

> 本模块直接对应项目已经实现的会话内上下文治理和跨会话买家偏好。需要特别区分：LangGraph Checkpoint 保存执行状态，Context Governance 决定本轮给模型看什么，Preference Store 保存跨会话业务记忆；三者不是同一件事。

## 1. Agent 为什么需要 Memory？

模型调用本身近似无状态。没有 Memory，它不知道前面确认过的约束、工具执行结果、任务进度和用户长期偏好，每轮都要重新询问。Memory 的价值不是“保存所有文字”，而是让未来决策获得必要且可信的信息。

本项目需要记住两类内容：会话内的当前目标、约束、已完成步骤、有效事实；跨会话的 buyer 喜好、黑名单和历史选择。前者由 Checkpoint + 四层上下文治理处理，后者由 PreferenceStore 处理。原始 trace 仅用于审计，不应全部回灌模型。

## 2. Agent 的 Memory 通常分为哪些类型，各适合什么场景？

可按时间和用途划分：

- 短期/工作记忆：当前回合与任务必要状态，要求低延迟和强一致。
- 情景记忆：过去发生过的任务、选择和结果，适合复盘与个性化。
- 语义记忆：从多次经历沉淀的事实和偏好，适合跨会话复用。
- 程序性记忆：做事步骤、策略、Skill 或 Prompt，通常版本化管理。

项目中 D1/D2/D3 属于会话工作记忆，D4 保存可追溯原始 artifact；PreferenceStore 是跨会话语义偏好；Prompt 和 Harness 规则可视为程序性知识。项目尚未建立通用“过去会话向量检索”或自动经验学习系统。

## 3. 短期记忆、长期记忆和三层记忆分别如何设计和实现？

短期记忆应绑定 thread/run，通过 Checkpoint 保存消息与执行状态，同时在模型调用前做投影和压缩。长期记忆应绑定可信 buyer，而不是 thread，采用结构化记录、来源、时间、置信度、删除和冲突策略。

常见三层设计可理解为：热层保存当前必要内容；温层保存结构化摘要/工作记忆；冷层保存完整事件和 artifact。项目进一步拆成 D1 热上下文、D2 结构化任务状态、D3 可更新工作记忆、D4 冷数据。长期偏好另行存 SQLite，通过中间件按需投影进 D3，不把整个偏好数据库塞入 Prompt。

## 4. 三层记忆设计中，如何平衡存储成本、检索效率和信息质量？

热层容量小但每轮读取，必须只保留高价值数据；温层做增量更新，避免反复总结；冷层可便宜存完整原文，通过引用按需恢复。升级/降级由访问频率、决策重要性、大小、可信度和时效共同决定。

项目将当前用户请求、最近工具结果和未闭合调用放 D1；目标/约束/计划放 D2；已验证事实和失败路径放 D3；大工具结果和 trace 放 D4。这样高频 Prompt 小而稳定，同时保留审计和恢复能力。

## 5. 为什么有的记忆方案使用 Markdown 而不是 RAG？数据规模扩大后是否仍然适用？

Markdown 可读、可 Git 版本化、适合少量稳定的程序性知识和人工维护偏好；无需向量服务，确定性强。RAG 适合规模大、查询局部相关、内容经常变化的集合。选择取决于访问模式，不是技术先进程度。

规模扩大后，单个 Markdown 全量注入会增加 Token 并降低准确性。可把 Markdown 作为事实源，离线解析成结构化块后建立关键词/向量索引；项目的 `knowledge/*.md` 正是这样：原文保留，离线生成品类卡，在线检索卡片。用户偏好量较小且结构化，直接数据库过滤比 RAG 更合适。

## 6. 记忆更新时如何保证语义匹配可靠？发生误判会造成什么问题？

不能只靠 Embedding 相似就覆写旧记忆。应先识别实体、记忆类型、作用域和极性，再用稳定 key 或规则匹配；模型提取结果要过 Schema；高风险变更要求确认；保留来源、时间和旧版本。

误把“这次不要红色”写成永久讨厌红色，会持续错误排序；把不同品牌/地区偏好合并，会污染推荐。项目用显式 `remember_preference/forget_preference` 工具和 like/dislike 结构写入，buyer 从可信 ContextVar 取得。进一步可增加作用域和证据字段，区分临时约束与长期偏好。

## 7. 长期记忆出现冲突时如何处理？

先按作用域、时间和证据强度判断：本轮明确指令优先于历史；更具体的品类/场景偏好优先于全局；显式纠正优先于模型推断；仍冲突则保留两条并追问，不能静默覆盖。

项目中 dislike 作为硬负向信号，like 作为软排序信号，本轮 ProductSearchSpec 的预算、目的地等硬约束优先。删除通过 `forget_preference` 显式完成。当前模型较简单，未来应给偏好增加 scope、source、confidence 和 valid_from/to，使冲突解决可解释。

## 8. 历史记忆如何设计淘汰策略？

可综合 TTL、最近使用、访问频率、置信度、业务重要性、重复度和用户显式保护。负面安全/黑名单信息不能与普通喜好用相同 LRU；删除还要支持用户权利和审计要求。

项目策略是 dislike 不因容量自动裁剪，like 有容量上限并按价值选择；语义缓存键包含 buyer 与完整偏好指纹，偏好变化后旧缓存自然失效。会话 D3 可淘汰，D4 原始 artifact 仍可恢复。生产化还需数据保留期、隐私删除和归档任务。

## 9. Context Window 是什么？为什么长上下文可能导致模型效果下降？

Context Window 是一次推理能接收和生成的 Token 总范围。更长不等于更好：注意力被无关内容稀释，关键事实可能处于“中间丢失”位置；冲突指令增多；推理延迟和费用上升；KV Cache 占用增大；工具大结果会挤掉真正必要消息。

因此项目不把 Checkpoint 中全部历史直接交给模型，而在每次模型调用前构造投影，只放稳定前缀、当前任务状态、相关工作记忆和 D1 热消息。

## 10. 上下文工程在对话系统中有什么作用？主流上下文工程技术有哪些？

上下文工程是为每次模型调用选择、组织、压缩和验证输入。技术包括角色/顺序设计、RAG、结构化状态、滑动窗口、摘要、消息裁剪、artifact offload、工具动态加载、长期记忆检索、缓存前缀设计和权限过滤。

本项目把它视为应用治理而非简单 `messages[-N:]`：L0 工具输出先清洗；D1–D4 分类；Cache Epoch 管理稳定基线；确定性策略先裁剪；接近阈值才用 LLM 生成增量 D2/D3；所有变化都通过 Pydantic delta 校验，D4 保留原文引用。

## 11. 多轮对话中如何管理上下文和对话状态？

需要分别管理原始事件、业务状态和模型视图。原始事件追加保存便于恢复；业务状态用结构化字段增量更新；模型视图在每轮调用前根据预算重新投影。不能从自然语言历史反复“猜”订单、任务或约束状态。

项目用 LangGraph `thread_id` 恢复消息/图状态，Context Middleware 识别 D1 protect set，投影 D2/D3，必要时压缩并更新 Cache Epoch。Preference Middleware 再按 buyer 注入跨会话偏好。外层 `shopping_session_id` 用于业务和事件路由，三种标识职责不同。

## 12. 如何避免上下文溢出、关键信息丢失或 Agent 遗忘重要内容？

先做输入预算和 Token 估算，按信息等级设置硬保护：当前请求、未闭合工具调用、用户纠正、业务约束不可丢；旧原文可 artifact 化；结构化任务状态不能被自然语言摘要替代。压缩后还要做完整性校验，并保留可恢复引用。

项目的 D1 永远保护；工具调用与结果成组处理；D2 只允许 validated patch；D3 增量 upsert/delete；大型输出进入 D4。若仍溢出，紧急路径只保留 L1 基线、D2、最小 D3 和 D1，重试一次，而不是无限压缩。

## 13. 上下文压缩和裁剪如何实现？为什么需要压缩？压缩后丢失细节如何处理？

裁剪是确定性删除/截断低价值内容，便宜且可预测；压缩是把多个事件转成更短的语义表示，通常更完整但会引入模型误差。合理顺序是先去重、清洗、大结果外置和规则裁剪，再在确有必要时调用 LLM。

项目的 LLM 压缩不是重写所有历史，而只处理当前 Cache Epoch 动态区中、Breakpoint 之后且不属于 D1 的候选事件，输出 `task_state_patch`、working-memory upsert/delete 和 archive refs。前面的稳定基线不变，原始细节写入 D4，可按引用找回；压缩模型不能删除 D1。

## 14. 滑动窗口与动态摘要有什么区别，分别适合什么场景？

滑动窗口保留最近 N 条/Token，速度快、确定性强，但可能丢掉很早却重要的约束；动态摘要能跨越长历史保留语义，但增加调用成本、延迟和错误传播。短闲聊适合窗口，长任务更适合“结构化状态 + 增量摘要 + 热窗口”。

项目采用后者：D1 相当于语义感知的热窗口，D2 永久保留当前任务结构，D3 保存阶段性事实；只有达到策略阈值才触发摘要。不会每轮从头总结，也不会简单按消息条数一刀切。

## 15. 长文本的摘要和关键信息提取如何实现？

先按结构/语义边界分块，每块提取带来源的事实，再归并去重；输出固定 Schema，包括事实、约束、结论、不确定性和引用；用分层 map-reduce 或滚动增量处理超长内容。数字、否定、时间、实体必须重点校验。

项目品类知识不是在线随意摘要：Markdown 变化时离线调用结构化 LLM 一次，生成 CategoryCard，并保存 `raw_evidence` 和 manifest，之后在线重复使用。会话压缩也要求模型只返回增量 Delta，应用策略验证后原子应用。

## 16. 除了向量检索，还可以用哪些方式从长对话或历史记忆中找回关键信息？

可以使用稳定 key/实体索引、关键词/BM25、时间窗口、结构化 SQL、标签/作用域过滤、知识图谱、任务 DAG、事件类型索引以及用户显式书签。对于金额、订单 ID、黑名单等精确事实，结构化查询通常优于向量。

项目的偏好按 buyer 和类型查询，任务按 task/thread 状态查询，Checkpoint 按 thread 恢复，D4 用 artifact ref 定位；语义缓存才使用 Embedding。未来若做通用情景记忆，可将结构化过滤与向量召回融合，而不是只建一个大向量库。

## 17. 如何控制和优化 Agent 的 Token 消耗？Token 消耗异常增大时如何排查？

控制手段包括：稳定短 System Prompt；按需工具 Schema；D1–D4 上下文投影；大结果外置；增量而非全量摘要；轻重模型分层；总预算和每阶段预算；缓存稳定前缀；限制 Agent 轮次和并发分支。

项目 ModelGateway 支持主/轻量/最小/备用档位，预算比例决定模型层级；同一预算可向 fork 任务传播。排查时按 trace 分解输入、输出、工具结果、摘要和各子 Agent Token，观察 Cache Epoch 重建、重复同参调用、工具 JSON 膨胀或子任务过度拆分。CTX-001 的本地候选 A/B/C 已测得 `full` 相比 `off` 输入 Token 降低 32.21%、信息保留率 100%、同 Epoch 前缀 Hash 稳定率 100%；供应商虽返回部分缓存 Token，当前实验仍不把前缀稳定率换算成“缓存命中 80%”。
