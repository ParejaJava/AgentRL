# 七、LLM、Transformer、训练、推理与多模态基础

> 真实性说明：本项目调用兼容 OpenAI API 的 Kimi K2.6，并在本地运行 BGE-M3 与 BGE-reranker-v2-m3；没有预训练/SFT/RL 大模型，也没有实现多模态 Agent。本模块后半部分是面试理论与“若应用到本项目”的分析，不是项目业绩。

## 1. 大语言模型从接收 Prompt 到输出结果，中间经历了什么过程？

应用先把 System/User/Tool 等消息按模型模板序列化；Tokenizer 将文本变成 Token ID；Embedding 层把 ID 映射成向量并加入位置信息；多层 Transformer 通过 Self-Attention 和前馈网络计算上下文表示；输出层得到下一 Token 的 logits；采样策略选出 Token，追加后重复自回归过程，直到停止符、长度或工具调用结构完成。

Agent 场景还多一层宿主循环：若输出是 tool call，LangGraph 执行工具并把 ToolMessage 加回上下文，再开始下一次模型推理。模型内部生成与外部 AgentLoop 必须区分。

## 2. 输入给大模型的内容本质是什么？Token 如何生成和处理？

输入最终是整数 Token ID 序列，不是 Python 字符串。Tokenizer 常用 BPE、WordPiece 或 SentencePiece，把文本切成词、子词、字符或字节片段，并加入 BOS/EOS、角色边界和工具控制 Token。相同字符在不同模型上 Token 数可能不同。

项目做上下文预算时必须使用目标模型的 Tokenizer 或可靠估算，不能用字符数等同 Token。工具 JSON、中文英文混合、长 URL 都可能显著改变 Token 数。

## 3. 模型为什么不能直接理解自然语言？

计算机只能处理数值。模型通过训练学习 Token 共现、语义和任务规律，把离散符号映射到连续表示；所谓“理解”是这些表示和参数支持了预测、推理与泛化，并非直接接触字符串意义。

因此模型输出是概率性的，也不知道外部世界的实时状态。项目必须通过工具提供商品、偏好和订单数据，并由代码验证，不能把模型语言流畅等同于事实正确。

## 4. Token 与 Embedding 分别是什么？

Token 是分词后的离散单元，对应一个词表 ID；Embedding 是该 ID 或整段文本的连续向量表示。LLM 输入 Embedding 会随 Transformer 层与上下文更新；检索 Embedding 通常把 Query/文档压成固定维向量用于相似搜索。

项目中 Kimi 的内部 Token Embedding 不由应用直接管理；BGE-M3 生成的是检索向量。二者虽然都叫 Embedding，目的和粒度不同。

## 5. GPT 为什么采用 Decoder-only 架构？

Decoder-only 使用因果 Mask，只允许每个位置看当前及之前 Token，天然符合“根据前文预测下一个 Token”的生成目标。统一的输入输出序列便于把问答、代码、工具调用都转成文本续写，也易扩展规模和复用 KV Cache。

Encoder-only 如 BERT 更擅长双向理解、分类和表示；Encoder-Decoder 适合显式输入到输出的转换。项目生成模型用 Decoder-only API，BGE 检索/重排则属于更偏表示和匹配的模型角色。

## 6. Self-Attention 的机制是什么？Q、K、V 为什么这样设计，如何计算？

对输入矩阵 `X` 做线性投影：`Q=XWq`、`K=XWk`、`V=XWv`。注意力为 `softmax(QK^T / sqrt(d_k) + mask)V`。Q 表示当前位置想找什么，K 表示每个位置可被匹配的特征，V 是匹配后聚合的内容；缩放避免维度大时点积过大导致 softmax 饱和。

多头注意力用多组投影学习不同关系，再拼接。Decoder 的因果 Mask 阻止看未来 Token。其标准复杂度随序列长度近似平方增长，这也是长上下文成本的重要来源。

## 7. 同一个 Token 在不同位置对应的向量是否相同？为什么 Attention 能捕获上下文信息？

最初的词嵌入相同，但加入绝对/旋转等位置信息后，不同位置表示不同；经过每层 Attention，它还会聚合周围 Token，形成上下文化向量。所以“bank”在金融和河岸语境中的高层表示不同。

Attention 的 QK 相似度决定当前位置关注哪些历史位置，V 把相关内容带入当前表示；多层堆叠后可组合局部和远程关系。长序列并不保证所有位置同等利用，因此项目仍需上下文分层和检索。

## 8. Temperature、Top-K、Top-P 分别有什么作用？

Temperature 用 `logits/T` 调整分布：T 小更尖锐，T 大更随机。Top-K 只在概率最高的 K 个 Token 中采样；Top-P 选择累计概率达到 P 的最小集合。它们作用于解码而非模型知识。

工具调用、结构化提取和会话压缩通常使用低随机性；创意文案可适当提高。项目曾发现当前 Kimi 接口不接受显式 `temperature`，因此模型工厂需按供应商能力省略不支持参数；“配置了 0.1”并不保证请求被兼容。

## 9. 为什么 Temperature 设为 0 后，模型输出仍可能不完全一致？还有哪些因素影响推理确定性？

0 通常意味着贪心选最大概率，但并不保证整个服务确定：相同最高分可能 tie；GPU 并行浮点归约、量化和算子非确定；服务端模型/路由变化；动态批处理；Prompt 或工具顺序变化；外部数据变化都会影响结果。

要提高复现性，应固定模型版本、Prompt、工具 Schema 顺序、输入、seed（若支持）、解码参数和依赖数据，并记录 trace。Agent 中工具时间、搜索索引和并发完成顺序也必须固定或结构化处理。

## 10. 哪些情况下容易出现模型幻觉？

缺乏知识或知识过时、问题含错误前提、检索证据不足/冲突、上下文过长、强迫必须回答、要求精确数字/引用、工具失败但错误被隐藏、采样随机性高时都容易幻觉。

项目的缓解方式是：商品和知识走检索；到手价由代码计算；空结果允许明确失败；订单必须验证；工具结果保留证据；Safety/Context 中间件不把外部内容当系统指令。仍需增加最终答案证据支持度评测。

## 11. KV Cache 是什么，为什么能提升推理速度？

自回归生成每个新 Token 时，历史 Token 的 K/V 在每层已经算过。KV Cache 保存它们，新一步只计算新 Token 的 Q/K/V 并与缓存交互，避免重复计算整个前缀。代价是显存随层数、序列长度、batch 和 KV head 数增长。

Prefix/Prompt Cache 还可跨请求复用相同前缀的计算。项目的 Cache Breakpoint/Epoch 目标是保持 System Prompt、工具和稳定基线不变，把动态内容放后面，提高供应商缓存机会；它与会话压缩的语义边界相关但不是同一个概念。

## 12. 如何提升线上大模型或 Agent 的吞吐量并降低延迟？

模型侧可用连续批处理、KV/Paged Attention、量化、投机解码、较小模型路由、并行和更短输出；应用侧可缩短 Prompt、缓存稳定前缀/Embedding/语义结果、并行独立工具、流式返回、连接池、异步 I/O、超时和降级。

项目已有全局并发信号量、请求最小间隔、主/轻/最小/备用模型档位、上下文压缩、Embedding/语义缓存、fork 并行和 SSE Token 流。尚未做真实生产压测和动态 batching，因为远程模型推理由供应商负责。

## 13. 大模型部署需要考虑哪些因素？

包括模型许可与精度、显存/算力、量化、上下文长度、并发、首 Token/每 Token 延迟、可用性、弹性、模型版本、数据隐私、监控、成本和灾备。还要决定 API 托管还是自部署。

项目生成模型走远程兼容 API；BGE 模型本地部署，需要处理 GPU/CPU 选择、离线模型路径和显存。Docker Compose 包含应用、worker、Redis、OpenSearch 等，但当前 Docker 服务未完成完整在线验收，不能说已生产部署。

## 14. GPU 显存如何估算？

粗略分为权重、KV Cache、激活/临时工作区和运行时开销。权重约为“参数量 × 每参数字节”：FP16/BF16 约 2 字节，INT8 约 1，4-bit 约 0.5，另加量化元数据。训练还要加入梯度和优化器状态，通常远高于推理。

KV Cache 与 batch、上下文、层数、KV heads、head dimension 和 dtype 近似线性。部署前应在目标框架实测峰值并留 10%–20% 余量。项目对 BGE Embedding/Reranker 提供显存适配：缩小 batch、候选量或退到 CPU，而不是硬编码假设。

## 15. BERT 等小模型与大模型相比有哪些优缺点？

BERT 类 Encoder 模型推理快、成本低、输出稳定，适合分类、NER、Embedding 和重排；但生成、开放式规划和 in-context 泛化弱。大模型能理解复杂指令和调用工具，但贵、慢且概率性高。

项目采用组合：LLM 做自然语言决策和 AgentLoop；BGE-M3 做召回向量；Cross-Encoder 做候选相关性；Pydantic/领域代码做规则。不是所有子任务都交给最大模型。

## 16. BERT 小模型的训练数据如何准备，训练和调优流程是什么？

先定义任务和标签，清洗去重、处理类别不均衡并按实体/时间划分 train/val/test 防止泄漏。分类任务构造文本—标签，检索任务构造 query—正样本—难负样本。加载预训练模型，设置任务头，微调并按验证指标早停，最后做阈值、校准、鲁棒性和推理性能评估。

项目没有自行训练 BGE/BERT。如果为工具路由训练小模型，应从 trace 标注意图/正确工具，重点构造相似工具难负例，并按会话拆分数据，避免同一对话进入训练和测试。

## 17. 模型调优通常有哪些步骤？如何选择超参数？

步骤是定义目标与基线 → 数据审计/划分 → 选择预训练模型 → 小规模搜索学习率、batch、epoch、warmup、weight decay、序列长度 → 监控训练/验证曲线 → 错误分析 → 独立测试 → 部署回归。优先从官方建议范围做随机/贝叶斯搜索，不在测试集调参。

除了效果，还要看延迟、显存、校准和分桶公平性。项目当前只有推理集成，没有训练超参实验，面试中应明确这一边界。

## 18. Agentic CPT、SFT、RL 三阶段训练分别是什么？

CPT（Continued Pretraining）用大量领域/交互语料继续下一 Token 训练，注入领域分布和基础能力；SFT 用高质量指令—响应或工具轨迹教模型按格式完成任务；RL 再用奖励优化长期任务成功、偏好或安全，可采用 PPO/GRPO 等在线方法或相应偏好优化路线。

三者成本和风险逐级增加。Agentic 数据应包含状态、动作、工具观察和结果。项目未执行这三阶段；目前通过 Prompt、RAG、工具/Harness 和评测增强通用模型。

## 19. SFT 时为什么要 Mask Observation Tokens？

工具 Observation 是环境提供的结果，不是模型应学习生成的动作。若对 Observation 也计算语言模型损失，模型会被训练去“编造工具结果”，并浪费容量记忆不可控内容。通常只对 Assistant 的决策、tool call 和最终回答计算 loss，System/User/Tool observation 标签设为 ignore（如 `-100`）。

具体是否 Mask 要看训练目标：若训练环境模拟器，则另当别论。当前项目不做 SFT，但保存规范 tool trace 可为未来构造正确的 loss mask 数据。

## 20. 多模态大模型的结构是什么？视觉编码器与语言模型如何衔接？

常见结构是视觉编码器（ViT 等）把图像切 patch 并编码，projector/resampler/Q-Former 将视觉特征映射到 LLM 隐空间，作为视觉 Token 与文本 Token 一起进入 LLM；训练分为对齐预训练、指令微调和偏好/安全阶段。视频还需时间采样和时序建模。

另一类原生多模态模型从训练开始统一多种 Token。无论哪种，模型仍需工具完成 OCR 后校验、搜索和外部行动。

## 21. 多模态或视频生成 Agent 与纯文本 Agent 有哪些区别？

多模态 Agent 的状态包含图片、音频、视频和时间轴，工具包括感知、编辑、渲染和资产存储；上下文成本更大，必须用缩略图、关键帧、embedding 和 artifact 引用。生成任务通常异步长耗时，还涉及版权、内容安全和可视化验收。

当前项目是文本和结构化商品卡，不支持图片理解或视频生成。若扩展商品图分析，应将媒体放对象存储，在上下文只传引用/描述，使用独立视觉 Agent 或工具并保留来源。

## 22. 如何评估多模态或生成式模型的输出质量？

需要自动指标与人工评审结合。图像可看 CLIP/语义一致、FID/KID（分布质量）、OCR/布局准确、感知质量和安全；视频增加时序一致、运动合理和闪烁；任务型 Agent还看指令遵循、事实、工具成功和延迟。

自动指标不等于用户审美，应设计盲评 rubric、成对偏好和分桶案例，并检查版权/偏见/敏感内容。当前项目没有此类评测，不能把文本召回指标迁移为多模态质量结论。
