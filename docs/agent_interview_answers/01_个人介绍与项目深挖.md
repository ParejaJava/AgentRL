## 2. 请介绍一段最有代表性的实习或项目经历，说明项目背景、目标、整体架构、核心流程、技术选型、个人职责和最终产出。

**参考回答：**

项目背景是跨境购物决策比普通搜索复杂：用户会提出模糊需求，系统需要补齐品类知识、跨平台搜索候选、结合收货地估算运费与关税、应用长期偏好，并把复杂请求拆成可并行任务。单次模型问答难以同时解决工具选择、长上下文和可靠性问题。

目标是构建一个 Agent 平台原型，而不是绑定某一家购物网站。架构采用 DDD-lite + Hexagonal：

- `domain` 保存 Product、Money、Shipping、Tariff、Preference、Order 等纯业务对象；
- `application` 保存搜索、订单、任务 DAG、编排、上下文策略等用例和端口；
- `infrastructure` 实现 LangGraph、模型、FAISS、OpenSearch、SQLite、Redis、LangFuse 等适配器；
- `presentation` 用 FastAPI 暴露 SSE、WebSocket、订单和异步任务接口；
- `composition.py` 是唯一装配入口。

核心流程是：请求 DTO 校验后生成可信 `ShoppingContextSnapshot`；应用层进行输入安全检查和可选语义缓存；主 Agent 进入 LangGraph ReAct 循环；上下文中间件在每次模型调用前投影稳定前缀、结构化状态、热消息与冷引用；模型可直接调用检索工具，也可通过 Task 四工具构建 DAG，再调用 `fork_sub_agents` 并行执行隔离子任务；工具结果经过超时、熔断、Schema、顺序和注入检查；最后通过 SSE/WebSocket 发布事件并按条件写入缓存。

技术选型上，LangGraph 用于状态图、持久化和 Agent Loop；FAISS 负责商品本地向量召回；OpenSearch 负责品类知识 BM25+KNN Hybrid；BGE-M3 负责向量编码，BGE Reranker v2-m3 负责交叉编码重排；SQLite 保存偏好、任务、订单和检查点；Redis 用于跨进程事件、Stream 队列、共享熔断和缓存。

个人职责可表述为：[根据实际情况说明你负责的比例]。仓库可证明的产出包括 12 个主 Agent 工具、同构子 Agent 执行器、两套召回评测、37 张结构化品类卡片以及 170 项最终代码回归测试。商品冻结集的 Recall@10 为 96.27%、MRR@10 为 93.22%、NDCG@10 为 92.58%；正式表达必须引用 `SEARCH-001` 和 `TEST-001` 快照。

## 4. 项目各模块是如何协作的？从请求进入到结果返回，完整工作流是什么？

**参考回答：**

入口是 `app/presentation/server.py`。`AgentRequest` 校验 message、shopping session、buyer、locale、currency 和 thread，然后映射成 `RunAgentCommand`。`shopping_session_id` 用于业务事件分区，`thread_id` 用于 LangGraph 短期对话状态。

`RunAgent.execute` 先发布 `run.started`，再执行提示注入检测；如果开启语义缓存，只允许首轮只读查询命中。之后创建 `AgentExecutionContext`，通过 ContextVar 绑定给整条异步调用链，并进入 `MainAgent.stream`。

`MainAgent` 使用 LangChain `create_agent` 生成 LangGraph ReAct 图。模型调用前依次经过模型网关、工具 Harness、工具韧性、偏好注入和上下文治理。模型可以调用 `item_search`、`category_insight`，也能使用 TaskCreate/Get/List/Update 和 `fork_sub_agents`。子 Agent 复用相同模型、中间件、状态 Schema 和检索工具，但每次生成新的 `sub-*` thread，只把最终回答回传主 Agent。

工具结果以 `ToolMessage` 返回图状态，过程中被映射成 `tool.invoke`、`tool.result`、`agent.dispatch`、`context.compressed` 等稳定事件。最终文本经过输出脱敏，发布 `token.delta`、`final.result` 和 `run.finished`。Redis 开启时事件可跨 API/worker 进程广播，否则使用内存事件总线。

## 5. 项目中最有挑战的部分是什么？遇到的最大技术难题是什么，如何定位并解决？

**参考回答：**

最有挑战的是同时解决长上下文与 Prompt Cache 稳定性。简单滑动窗口会丢任务状态；每轮全量摘要会改变 Prompt 前缀，使服务端 KV/Prompt Cache 难以命中；把完整工具 JSON 留在历史里又会快速撑满上下文。

定位时把进入模型的信息拆成四层：工作记忆、结构化任务状态、热消息和冷数据，再检查每层是否必须进入 Prompt。最终设计 Cache Breakpoint：断点前的 L0 静态提示与 L1 Epoch Baseline 保持稳定；断点后的动态消息按 D1-D4 执行工具清洗、大结果卸载、确定性裁剪和增量 LLM 摘要。只有超过阈值才滚动 Epoch，避免每轮重写前缀。

另一个实际问题是 Kimi K2.6 对 temperature 和 thinking 参数有特殊约束。真实 SSE smoke 返回“只允许 temperature=1”。定位到模型适配器后，对 Kimi/GPT 推理模型省略 temperature，并在结构化摄取与压缩任务中关闭 thinking，最终真实 API 流恢复正常。

## 6. 项目上线后出现过哪些问题或 Bad Case？你如何排查、定位、修复和持续优化？

**项目真实口径：**

当前项目没有生产上线，因此应回答“开发和端到端验证阶段的 Bad Case”，不能虚构线上事故。

典型问题一是模型下载完成后仍访问 Hugging Face。原因通常是本地缓存目录结构、revision 或环境变量不匹配。排查路径是先验证模型目录和关键 tokenizer/config 文件，再检查 `HF_HOME`、离线模式和模型名，最后分别做 encoder/reranker 最小加载。项目把模型加载集中到工厂，并增加 GPU/FP16/batch 配置和三级检索降级，模型不可用时还能回退到词法检索。

典型问题二是品类结构化摄取失败。模型可能返回不存在的 card type、超过三条 evidence，或者把证据改写成原文不存在的句子。修复方式是在 Pydantic Schema 中校验不同卡片的业务载荷，用 JSON mode 重试，对 evidence 做原文行锚定，并在所有文档成功后原子写入卡片和 manifest。

典型问题三是 Harness 声明了工具前置关系，但恢复会话后进程内调用历史为空。最终规则是：本轮已有工具轨迹且缺前置工具时硬拒绝；完全无历史时降级告警，再依赖订单服务自身的商品、SKU、确认和幂等校验，避免误杀由 Checkpointer 恢复的合法状态。

## 7. 如何证明项目或 Agent 的效果确实得到了提升？使用了哪些指标、实验或对照方法？

**参考回答：**

需要把 Agent 效果拆层评估，不能只看最终回答“感觉不错”。项目当前最完整的是检索评测：商品集有 67 条查询，统计 Recall@K、Precision@K、MRR 和 NDCG@K；品类卡片集有 100 条，除四个排序指标外还统计负例拒答率。

商品召回实测 Recall@5=95.52%、Recall@10=96.27%、MRR@10=93.22%。对照应使用词法基线、向量召回、融合召回、重排后结果分别跑同一数据集，避免把数据变化当算法提升。品类本地词法降级基线 Recall@5 只有 46.11%，这不能写成最终 RAG 指标；OpenSearch Hybrid 必须在服务启动后单独评测。

Agent 运行层通过 170 项最终代码回归测试覆盖上下文、任务 DAG、fork、工具签名、价格、订单、偏好、事件和降级；12 个场景 × 3 次 Kimi 候选实验评估工具路由、DAG/Fork、约束与最终回答，并从 Langfuse 回读 3 条完整主/子 Trace。当前尚缺线上 A/B 和真实生产流量，因此简历中不能把本地候选扩大成生产收益。

## 8. 项目解决了什么真实业务问题？产生了怎样的业务价值？

**参考回答：**

它解决的是跨境购物决策信息分散的问题：用户通常不知道该搜什么参数，也难以同时比较商品事实、材质常识、目的地运费、关税和自己的历史偏好。平台把这些步骤组织为可审计工具链，并允许复杂请求并行处理。

具体价值包括：品类知识帮助用户形成搜索词和精挑标准；商品搜索返回可购买候选；传入 `ship_to` 时内联估算商品价、运费和关税；跨会话偏好用于过滤黑名单和个性化排序；订单意向把用户确认后的选择持久化。工程上，端口隔离让检索、模型和数据库可替换，事件流让前端能展示进度。

目前价值是“可运行原型与工程验证”，没有真实 GMV、转化率或线上节省工时数据。业务结果应等接入真实商品源和用户实验后再补。

## 9. 为什么选择当前的 Agent 架构，而没有选择普通 Workflow 或其他方案？

**参考回答：**

跨境购物请求的步骤不是固定的。有人只问一个价格，有人需要先查品类常识、再搜四个平台、按偏好筛选并估算到手价。固定 Workflow 要为所有组合预设分支，扩展成本很高，因此让主 Agent 负责动态选工具更合适。

但项目没有把一切都交给模型。订单确认、任务 DAG、并发认领、价格计算、上下文压缩阈值、缓存资格和熔断都由确定性代码控制。可以概括为“Agent 负责开放式决策，Workflow/领域服务负责不可违反的约束”。

## 10. 为什么选择当前模型？是否比较过其他模型，选型时如何权衡效果、延迟、成本和上下文长度？

**项目真实口径：**

当前 `.env` 使用 OpenAI-compatible 的 Kimi K2.6，代码也支持通过 `LLM_MODEL_NAME` 切换模型，并可配置 `FALLBACK_LLM_MODEL` 和 `LITE_LLM_MODEL`。选择原因是长上下文和工具调用能力适合复杂 Agent 原型，同时兼容 ChatOpenAI 接口，便于替换。

仓库尚没有一份覆盖多个大模型的系统 benchmark，所以不要声称已经证明它最优。正式选型应固定同一批任务，比较任务成功率、工具调用准确率、JSON 合规率、首 Token 延迟、总延迟、输入/输出成本、上下文上限和限流稳定性。项目的四档 Token 预算为未来按成本动态切换主/轻量模型预留了运行时能力。

## 11. 项目中为什么选择 Python 或 Java？是否考虑过其他语言？Python 和 Java 在 Agent 开发中各有什么优势？

**参考回答：**

项目选择 Python，因为 LangChain、LangGraph、FlagEmbedding、FAISS 和主流模型 SDK 的 Python 生态成熟，适合快速实验检索、Prompt 和 Agent Loop；FastAPI 与 asyncio 也能满足 I/O 密集的 API、模型和工具并发。

Java 的优势是成熟的企业治理、强类型、大型团队协作、线程与性能诊断工具，以及与既有交易系统集成。若真实订单、支付和库存属于 Java 微服务，我会保留 Python Agent 编排层，通过 HTTP/MQ/MCP 调用 Java 领域服务，而不是在 Python 中复制交易核心。高性能本地推理或索引底层还可以使用 C++/Rust，由 Python 绑定调用。

## 12. 项目中用过哪些设计模式？工厂模式和责任链模式分别适合什么场景？

**参考回答：**

项目使用了工厂、适配器、端口与适配器、仓储、策略、装饰器和责任链思想。`composition.py` 与各检索 `factory.py` 根据 Settings 装配模型、存储、工具和中间件；应用层只依赖 Protocol 端口；SQLite、Redis、FAISS、OpenSearch 是适配器；Context 策略和召回融合属于策略模式；`CachedEmbeddingEncoder` 是装饰器。

工厂模式适合隐藏创建复杂度和运行时选择，例如根据开关选择内存或 Redis EventBus、local 或 OpenSearch Retriever。责任链适合一组有顺序的横切处理，例如模型调用依次经过限流、预算、偏好注入、上下文投影，工具调用依次经过 Harness、超时和熔断。责任链要明确顺序和短路语义，否则同一个失败可能被重复计数。

## 13. 在团队中如何协作完成 Agent 开发，并推动技术选型和架构演进？

**使用说明：**该问题包含个人经历，仓库无法证明团队人数。以下是可采用的方法论，不应虚构实际团队故事。

我会先把系统拆为模型、编排、工具、领域服务、检索、评测和平台基础设施，并为每块定义输入输出契约。技术选型不靠口头偏好，而是用 ADR/设计文档记录目标、候选方案、风险和回滚路径，再用最小 PoC 和评测集验证。

在本项目中，对应做法是先沉淀上下文治理、Factory、Task 工具、架构重组和参考项目差距文档，再通过 Protocol 和 Composition Root 落地。团队协作时可让不同成员并行负责 adapter，但 domain/application 契约需要共同评审；合并前跑架构测试、单测、召回评测和 smoke。

## 14. 当团队成员对技术方案有分歧时，如何沟通并达成共识？

**参考回答：**

先把争议转成可验证问题，例如“固定专家 Agent 还是同构 fork”“Qdrant 还是 FAISS+OpenSearch”，分别列出业务变化频率、上下文隔离、部署复杂度、召回指标和迁移成本。然后约定同一数据集和成功标准做 time-boxed PoC，而不是讨论框架名气。

本项目的取舍例子是没有照搬参考项目的固定 SearchAgent/TradeAgent，而保留同构 LangGraph 子图：因为当前子任务主要是检索执行，同构图能复用状态 Schema、中间件和工具，同时用独立 thread 隔离上下文。若未来交易职责显著复杂，再基于数据拆成异构 Agent。

## 15. 如何保证复杂 Agent 项目的开发进度和交付质量？

**参考回答：**

把目标拆成垂直切片，每一阶段都要求“端口、实现、配置、测试、运行说明”同时完成。优先打通最短主链，再增加可选能力；所有外部依赖必须可关闭并有明确降级，这样 Redis、LangFuse 或 OpenSearch 未配置时不会阻断基础 Agent。

质量门禁包括 Ruff、单元测试、架构依赖测试、真实模型 smoke、召回回归和 Docker Compose 配置检查。对未验证的能力明确标注，例如当前 Docker daemon 未启动时不能声称完成容器级 Redis/OpenSearch 联调。

## 17. 使用 Claude Code 等 Coding Agent 时有哪些工作习惯？

**参考回答：**

第一，先给仓库级规则，例如所有 LangChain 工具必须使用 `@tool`、重要代码写中文注释、禁止替换既有架构。第二，让 Agent 先读项目和测试再改，避免根据文件名猜实现。第三，小步提交：先列计划，再实现一个垂直切片并运行定向测试，最后全量回归。

第四，严格审查边界：不允许把参考项目的实现直接覆盖现有方案，不允许把未跑的指标写成结果，不允许读取后泄露 `.env` 密钥。第五，要求输出可复现命令、改动文档和已知限制。Coding Agent 是加速器，不是责任主体。
