# 五、RAG、Embedding、检索与向量数据库

> 证据口径：品类知识引用 `RAG-001`，商品候选召回引用 `SEARCH-001`，两套指标禁止合并。

> 项目里有两套召回，但只有 `category_insight` 属于知识 RAG；`item_search` 是商品候选召回与排序。两者共享 BGE-M3/BGE-reranker-v2-m3 等技术，但数据单元、过滤条件和评测目标不同。

## 1. 什么是 RAG？企业应用为什么需要 RAG？

RAG 是先从外部知识源检索与问题相关的证据，再把证据提供给模型或下游决策，从而让答案基于可更新、可引用的私有知识。它降低参数知识过时和幻觉风险，也避免每次训练模型。

本项目的 `category_insight` 是 RAG：把 `knowledge/*.md` 离线转为结构化 CategoryCard，在线按品类查询召回卡片并返回证据、属性、爆款和价格层级。当前在线工具不再调用生成式 LLM；它返回已经结构化的知识供主 Agent 决策。

## 2. RAG 从数据处理、索引、召回、重排到生成的完整流程是什么？

通用流程是：采集与权限清洗 → 文档解析 → 切片/结构化 → Embedding 与词法字段 → 建索引 → Query 理解/改写 → 过滤 + 多路召回 → 融合 → Cross-Encoder 重排 → 拼装带引用上下文 → LLM 生成 → 证据校验与评测。

项目品类链路略有不同：Markdown 变更时，离线用结构化 LLM 一次性生成 Pydantic CategoryCard，保存精确原文证据和 manifest；在线 OpenSearch 用 BM25+KNN Search Pipeline 混合召回，再用 BGE-reranker-v2-m3 重排，最后工具直接输出压缩卡片。OpenSearch 不可用时走本地词法降级。生成答案发生在上层主 Agent，而非 RAG 工具内部。

## 3. 为什么不能把企业全部文档直接塞进 Prompt？

因为上下文有限，成本和首 Token 延迟随输入增长；大量无关内容会稀释注意力；权限难以按用户裁剪；文档更新会破坏缓存；模型也无法保证在长文本中正确定位证据。

项目只召回少量结构化卡片。原始知识文档保留为事实源，但不会全量进 Agent；会话中的大型工具结果也进入 D4 artifact。这样检索和上下文治理形成两道筛选。

## 4. 文档切片为什么重要？Chunk Size、重叠、边界和元数据如何设计？

Chunk 太大会混入多个主题并增加重排成本；太小会割裂语义，答案需要的证据散落。应优先按标题、段落、表格、列表等结构边界切，必要时再按 Token 限长；重叠仅用于跨边界连续语义。元数据至少含文档、章节、版本、语言、权限、时间和精确来源位置。

项目没有简单固定字符切片，而是把 Markdown 中的品类结论转为业务单元 CategoryCard：category、card_type、summary、raw_evidence、last_updated、confidence 等。检索单元更贴近工具输出，`raw_evidence` 保留 1–3 段证据，manifest 用于增量重建。

## 5. RAG 为什么要引入父子索引？

小块适合精确召回，大块适合给模型完整上下文。父子索引先以子块匹配 Query，再返回其父段落或相邻块，兼顾定位和可读性，同时去除同一父文档的重复结果。

项目当前以 CategoryCard 为主要检索单元，没有实现通用父子索引。因为知识已经被离线结构化，卡片本身同时承担细粒度匹配和可消费上下文。若未来加入长篇政策/测评，适合增加 child evidence chunk → parent section 的映射。

## 6. 什么是 Embedding？为什么向量可以表示语义？

Embedding 是模型将文本映射到稠密向量的过程。训练通过对比学习等目标，让语义相近的文本在向量空间更近、无关文本更远。因此向量相似度可作为语义相关性的近似，但它不是逻辑真值，也不天然理解业务过滤。

项目使用 BGE-M3 产生检索向量；商品和品类都保留词法通路，因为型号、品牌、SKU、数字等精确信号常常更适合 BM25/关键词。硬预算、币种、目的地也由结构化过滤处理，不能交给 Embedding 猜。

## 7. 如何选择 Embedding 模型或检索模型？

要看语言、领域、Query/文档长度、向量维度、吞吐、许可、部署资源，以及在自有数据上的 Recall/NDCG，而非只看公开榜单。还要确认模型要求的 instruction/prefix、归一化方式和相似度。

项目选择多语言 BGE-M3 处理中文、英文和跨境商品文本，重排使用 BGE-reranker-v2-m3。最终选型仍应通过 67 条商品、100 条品类评测做同集对照，并记录 full/vector-only/lexical 不同运行路径。当前没有完成多种 Embedding 模型的系统 A/B，因此不能宣称它绝对最优。

## 8. 向量数据库如何选型，其核心原理是什么？

核心是保存向量与元数据，用 ANN 索引在不扫描全部数据的情况下找近邻。常见算法有 HNSW、IVF、PQ；选型看规模、更新频率、过滤、混合检索、事务、运维和延迟。

项目商品本地检索使用 FAISS HNSW，适合单机原型和离线评测；品类使用 OpenSearch，原因是需要 BM25、KNN、过滤、Search Pipeline 和服务化。不是所有场景都需要独立向量数据库：规模小且以结构化过滤为主时，数据库扩展或本地索引足够。

## 9. 常见的向量相似度检索方法有哪些？余弦相似度如何计算？

常见有余弦相似度、点积和欧氏距离。余弦为 `cos(a,b) = (a·b) / (||a|| ||b||)`，只比较方向；若向量已 L2 归一化，余弦与点积等价，计算更快。欧氏距离关注绝对几何距离。

索引配置、训练方式和查询时度量必须一致。不能用一个模型按余弦训练，却在未归一化情况下随意改成点积，并直接比较不同模型的绝对分数。

## 10. 向量召回数量是否越多越好？如何确定合适的 Top-K？

不是。K 太小会漏召回，太大会增加重排和 Prompt 成本，并引入噪声。应根据候选覆盖曲线、重排容量、延迟预算和负例表现选择：观察 Recall@K 随 K 的边际收益，再确定 reranker 输入数和最终返回数。

项目评测同时报告多个 K，而不是只看一个最终点。商品最终展示数量受 ProductSearchSpec 的 `top_k` 限制；在线可先召回较多候选、融合后重排再截取。负例还应设置最低相关阈值，避免为了 Recall 强行返回无关卡片。

## 11. 如何构建企业 RAG 知识库？

除了技术索引，还要完成数据治理：确定来源与 owner、权限、版本、更新 SLA、解析质量、去重、PII/秘密处理、证据定位、增量索引、回滚和评测。索引必须携带 ACL，查询时先做身份过滤。

项目的品类知识库以仓库 Markdown 为权威源，离线结构化只处理变更文件，生成 JSONL 和 manifest，Pydantic 校验卡片，原文证据可追溯。当前是单租户原型，尚无企业 ACL 和内容审核工作流；若产品化，这是必须补充的部分。

## 12. 如何实现多维度 Query Rewrite？

可以从同义词、语言、实体、属性、品类、意图、过滤条件和多查询扩展。生成改写后应保留原 Query，分别召回再融合，避免单次改写误导全局。数字、品牌、否定和硬约束不应被自由改写。

项目主要通过结构化 ProductSearchSpec 将自然语言拆为 query、category、budget、currency、ship_to、top_k，再让词法与向量通道各自工作；`category_insight` 也可在搜索前给出更准确的属性词。当前没有独立的多 Query LLM rewrite 服务，可作为后续优化，但需用同一评测集证明收益。

## 13. Query Rewrite 发现信息不足时，如何触发用户补充信息？

先定义每种意图的必填槽位和信息增益。若缺失只影响排序，可使用默认值并说明；若影响可行性或高风险结果，则返回结构化 `needs_clarification`，包含缺失字段和一个最小问题，由 Agent 向用户追问。

项目中没有 `ship_to` 仍可搜商品，但不计算到手价；缺少订单 SKU、数量或目的地就不能创建购买意图。历史偏好只能提供软排序，不可擅自填充交易参数。

## 14. 为什么要并行化意图识别？如何实现并避免多个意图互相干扰？

当 Query 同时涉及分类、实体、风险、路由等独立判断时，并行可降低串行延迟。但每个分类器应只写自己的命名空间，最终由确定性聚合器解决冲突；共享模型并发还要受限流控制。

项目没有单独并行多个“意图模型”，而是由主 Agent结合 Prompt 与工具 Schema 做决策。复杂请求可通过 Task DAG 拆成独立商品搜索，再由 fork 并行；订单写路径不能与不确定的搜索任务混在同一并发写集合。

## 15. 召回阶段可以使用哪些策略？

包括 BM25/关键词、稠密向量、稀疏向量、字段过滤、规则/热门召回、多查询、同义词、父子索引、图检索以及行为协同召回。多路结果通常通过加权分数或 RRF 融合，再重排。

品类链路使用 OpenSearch BM25+KNN Pipeline，故障降级到本地词法；商品链路使用 BGE-M3 向量、FAISS HNSW、词法召回和融合，并用买家偏好做 UserTower 排序。三级降级保证 Embedding 或 reranker 挂掉时仍能返回可解释结果。

## 16. 为什么需要 Rerank？它应放在什么位置？

Bi-Encoder 预先独立编码 Query 和文档，适合大规模快速召回，但交互较粗。Cross-Encoder 把 Query 与每个候选一起输入，Token 之间可直接 Attention，相关性更准但计算昂贵。因此它放在多路召回融合之后、最终 Top-K 之前，只处理几十个候选。

项目使用 BGE-reranker-v2-m3 交叉编码重排。若 reranker 不可用，不中断检索，而保留融合/向量原序；再失败则走词法。这种降级路径也要分桶评测，不能把降级结果与 full path 混成一个指标。

## 17. BM25 与向量检索如何融合？

两路原始分数分布不同，不能直接相加。常见方法是各自归一化后加权，或用 Reciprocal Rank Fusion：对每路排名 `rank` 累加 `1/(k+rank)`。RRF 对分数尺度不敏感，适合作为稳健基线；权重融合可表达业务偏好，但需调参。

品类 OpenSearch Search Pipeline 负责 Hybrid 融合；商品本地服务也融合词法与向量候选，再进入重排。品牌、SKU 等精确词可给词法更大权重，口语语义 Query 则让向量发挥作用。

## 18. RAG 召回不准、相关性差或召回不足时，如何排查和优化？

按数据—切片—Query—Embedding—过滤—索引—融合—重排逐层排查。先看 gold 是否合理、文档是否入库；再检查解析/元数据；用候选列表判断是未召回还是排序靠后；分 Query 类型统计；最后才换模型。

项目用 Recall@K 判断漏召回，用 MRR/NDCG 判断排序；查看 `retrieval_mode` 区分 full/vector/lexical。品类本地词法基线 Recall@5=46.11%，只说明降级通路能力有限，不代表 Hybrid 最终效果；OpenSearch 未运行时不能用这个数冒充 RAG 最终指标。

## 19. 为什么检索内容明明相关，最终回答仍可能不准确？

可能是模型未正确使用证据、多个证据冲突、Prompt 没要求引用、上下文顺序不佳、工具输出被截断、问题需要计算或实时数据、模型把参数知识覆盖了检索事实。相关不等于足以回答。

项目通过结构化卡片减少自由解释；价格和关税由领域函数计算而非模型心算；证据保留 raw_evidence。未来还应增加 answer faithfulness/claim attribution 评测，因为当前召回评测只证明“卡片找到了”，不能证明最终自然语言完全忠实。

## 20. 如何判断问题出在检索阶段还是生成阶段？

保存每次 Query、候选、分数、重排结果和最终上下文。若 gold 证据不在候选，是召回问题；在候选但没进 Top-K，是排序/截断问题；已进入 Prompt 且足以回答，但答案错误，是生成/Prompt/推理问题。再用 oracle context：直接给正确证据，若仍答错则更能定位生成侧。

项目现有离线评测聚焦召回卡片和商品 ID；LangFuse/事件可以关联工具调用与最终回答。工具调用准确率、证据支持度和端到端购物决策仍是下一阶段评测，不应与召回指标混为一谈。

## 21. 如何评估 RAG 效果？

至少分三层：检索层 Recall@K、Precision@K、MRR、NDCG 和负例拒答；生成层正确性、faithfulness、引用命中和完整性；系统层延迟、费用、可用性与降级率。还要按语言、品类、难度、长尾、负例分桶。

项目品类有 100 条冻结测试数据，四个排序指标外单独统计负例。旧基线为 Recall@10=95.00%、MRR@10=70.77%、NDCG@10=74.95%、负例拒识率 0%；当前证据套件已使用独立开发集选择 0.01 阈值，再一次性验证冻结集。本地候选的 OpenSearch Hybrid + BGE 重排为 Recall@10=94.44%、MRR@10=80.37%、NDCG@10=81.79%、负例拒识率 90%。完整消融、延迟和失败样本引用 Claim `RAG-001` 与 `RAG-THRESHOLD-001`，正式投递仍需干净 Commit 快照。

## 22. RAG 项目中常见的线上问题有哪些，如何解决？

常见问题有索引延迟、Embedding 版本不一致、权限泄漏、空召回、重复块、热分片、重排超时、模型下载失败、缓存陈旧和 Query 分布漂移。解决要靠版本化索引、alias 原子切换、ACL filter、健康检查、降级、超时、监控和回归数据。

本项目开发中遇到 Hugging Face 网络/本地模型加载问题，因此加入本地路径配置、离线模式和显存适配文档；检索链路有 full → 无重排 → 词法降级。当前不是生产线上事故，应表述为本地集成与故障注入验证。

## 23. Elasticsearch 在 RAG 系统中起什么作用？如何优化检索性能和索引设计？

它们同时提供倒排索引、结构化过滤、聚合和向量 KNN，适合混合检索。索引设计要区分 text/keyword/numeric/vector；设置合适 analyzer、维度和 HNSW 参数；只返回需要字段；批量写入；使用 alias 做版本切换；监控 shard、heap、segment 和查询延迟。

项目选择 OpenSearch，并配置 Search Pipeline 做 BM25+KNN 融合，Docker Compose 部署。当前 Docker daemon 未启动时无法完成真实 OpenSearch 集成评测，所以本地词法只作为可用性降级。生产应进一步做权限、备份、容量和压测。

## 24. 是否了解 Graph RAG？它适合什么问题？

Graph RAG 抽取实体、关系、事件或社区，在图上做邻域/路径/社区摘要检索，再与文本证据结合。它适合关系密集、需要多跳推理和全局结构的问题，例如供应链关联、组织关系、风险传播；不适合简单 FAQ，也会增加抽取错误和维护成本。

当前项目未实现 Graph RAG。若未来要回答“品牌—母公司—产地—关税政策—替代商品”的多跳问题，可以在保留原文证据的前提下引入；对当前几十张品类卡和商品搜索，Hybrid 检索更经济。
