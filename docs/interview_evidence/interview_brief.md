# Globex Agent 面试速讲与数字口径

这份文档用于面试前快速复习。详细设计和原始证据从 [README](README.md) 跳转。

## 一句话定位

这是一个面向跨境购物决策的 Agent 平台：把品类知识、商品候选、用户偏好和跨境计价组合成可追踪、可恢复的决策流程，最终只创建订单意向，不代替真实电商平台完成交易。

## 90 秒口述版

我设计并实现了一个跨境购物多 Agent 平台。简单请求由主 Agent 直接调用品类 RAG、商品搜索、偏好或订单工具；复杂请求先形成 Task DAG，再把可运行任务原子认领给上下文隔离的子 Agent 并行执行。Agent Runtime 使用 LangGraph，但应用层只依赖端口，因此框架、模型、OpenSearch、Redis 和持久化实现都可替换。

我重点解决了三类问题。第一是编排可靠性：通过依赖 DAG、租约恢复、幂等回写和 settled 聚合，让单个 Worker 失败不丢失其他结果，30 轮 4 路 I/O 实验取得 3.43 倍 P50 加速，重复认领和上下文泄漏为零。第二是长会话：把上下文分成稳定基线、结构化状态、热消息和冷引用，在 Cache Breakpoint 后做确定性卸载与 LLM 增量摘要，真实 8 轮 A/B/C 实验把 AgentLoop 输入 Token 降低 43.30%，关键信息保留率 100%。第三是检索：品类知识用 OpenSearch Hybrid + BGE Reranker，商品用 BGE-M3 + FAISS + 交叉编码重排，并把偏好向量和黑名单规则加入排序。两套检索分开评测，同时验证 17 类故障降级和 36 次真实 Kimi 端到端场景。

## 六张 STAR 卡

### 1. 架构隔离（ARCH-001）

- S：Agent 框架、检索和购物规则耦合后，领域规则难单测，基础设施难替换。
- T：保护商品、Money、计价和订单不变量。
- A：采用 DDD-lite + Hexagonal，Application 只依赖 Domain/端口，LangGraph、OpenSearch、Redis 等放在适配器层，并以 AST 测试约束依赖方向。
- R：正式报告中静态依赖违规为 0；170 项测试通过，Domain 行覆盖率 93.19%，Application 行覆盖率 85.79%，关键领域规则行/分支覆盖率 100%。

### 2. 多 Agent 编排（ORCH-001、E2E-001）

- S：独立搜索任务串行执行慢，长链任务又容易串扰上下文。
- T：并行提速，同时支持失败隔离、中断恢复和权限收敛。
- A：Task DAG + 原子认领 + Worker 租约 + 独立 `thread_id` + 最小工具集 + settled 幂等回写。
- R：30 轮 4 路 I/O 的 P50 由 240 ms 降到 70 ms，加速 3.43×；重复认领和上下文泄漏为 0，成功结果保留率 100%；12 场景 × 3 次真实 Kimi 运行 36/36 通过。

### 3. 上下文治理（CTX-001）

- S：大工具结果和历史消息持续累积，既增加 Token，又可能破坏稳定 Prompt 前缀。
- T：降低长会话输入量，同时保留当前约束、任务状态和用户纠正。
- A：四层投影、Artifact Offload、Breakpoint Hash、Cache Epoch、确定性治理和结构化增量摘要；摘要不产生净压缩时保留原文。
- R：`full` 相比 `off` 的 AgentLoop 输入 Token 从 43,974 降至 24,935，下降 43.30%；三种模式的信息保留率与同 Epoch 前缀稳定率均为 100%。7 次摘要尝试中 5 次产生净压缩，2 次安全拒绝。

必须主动补充：计入摘要模型后，`full` 总输入/输出为 44,460/3,638 Token，`off` 为 43,974/1,257 Token；这组实验尚未证明总成本下降，只证明主 AgentLoop 上下文规模下降。更长会话、更小摘要模型和降低触发频率是下一步成本实验。

### 4. 品类 RAG（RAG-001、RAG-THRESHOLD-001）

- S：纯关键词难处理语义改写，纯向量又容易对域外问题强行返回结果。
- T：兼顾召回、排序与拒答。
- A：Markdown 离线结构化为知识卡；在线做 BM25 + KNN 的 Hybrid RRF，再以 BGE Cross-Encoder 重排；阈值只在独立开发集校准。
- R：冻结集 Hybrid + Reranker 的 Recall@10 94.44%、MRR@10 80.37%、NDCG@10 81.79%、负例拒识率 90%。相较 keyword，Recall/MRR/NDCG 分别提高约 48.33/45.56/45.28 个百分点。

### 5. 商品搜索与个性化（SEARCH-001、SEARCH-PERSONALIZATION-001）

- S：词法召回覆盖高，但首屏排序不稳定；用户偏好只写进 Prompt 无法稳定影响商品顺序。
- T：保持召回门槛，提高前排相关性，并让画像真正进入检索链。
- A：BGE-M3 双塔召回 + FAISS + Cross-Encoder 重排，融合 User Tower，最后执行黑名单、预算和可购买性硬约束。
- R：最终 Recall@10 96.27%、MRR@10 93.22%、NDCG@10 92.58%，通过回归门槛；相较 lexical，MRR 和 NDCG 提高约 4.60 和 5.09 个百分点，但 Recall 下降约 1.99 个百分点。个性化定向集 MRR 提升 6.67 个百分点、NDCG 提升 3.83 个百分点。

### 6. 可靠性与可观测性（REL-001、OBS-001）

- S：Agent 最终失败可能来自模型、工具、检索、任务状态或上下文，只有最终错误很难定位。
- T：限制故障半径并保留可追踪证据。
- A：共享并发/Token 预算、退避、熔断、三级检索降级、Emergency Projection、统一事件协议与 Langfuse Trace。
- R：17 类故障注入 17/17 通过；E2E 抽样回读 3/3 Trace，其中 2 条满足完整主/子拓扑；上下文抽样回读 3/3，其中 1 条满足完整治理拓扑。两套抽样的 run/trace 映射率均为 100%。

## 检索结果应该怎么讲

商品搜索不能说“相较词法基线 Recall 提升”。真实结果是 lexical 的 Recall@10 为 98.26%，高于最终策略的 96.27%；最终策略的价值是 MRR 和 NDCG 分别提高约 4.60 和 5.09 个百分点，使相关商品更靠前。这个取舍在购物首屏比单纯扩大候选覆盖更重要，但仍以 Recall≥95% 为底线。

品类 RAG 可以说 Hybrid + Reranker 显著优于 keyword；但相较未重排的 Hybrid RRF，重排后的 Recall 下降约 1.11 个百分点，同时 MRR 提高约 8.93、NDCG 提高约 6.21、负例拒识提高 90 个百分点。它优化的是排序和域外拒答，不是所有指标同时上涨。

## 高频追问短答

**为什么子 Agent 能复用图又隔离上下文？** 复用的是模型节点、工具节点、条件边、中间件和停止逻辑；每次执行使用独立 State、`thread_id` 和持久化目录，因此不复用消息历史。

**什么时候 fork？** 当前任务可并行、需要上下文隔离、预计调用链达到三层，任一条件成立即可建议 fork；真正可运行的任务还要通过 DAG 依赖检查和原子认领。

**Breakpoint 为什么能帮助缓存？** 它定义同一 Cache Epoch 内不可改写的稳定前缀，并记录 Hash；压缩只处理边界后的闭合历史。供应商没有返回真实缓存 Token，所以这里只证明前缀稳定，不宣称 Prompt Cache 命中率。

**上下文压缩是否真的省钱？** 当前不能这么说。主 AgentLoop 输入减少 43.30%，但 8 轮实验中摘要调用抵消了节省，`full` 总 Token 反而略高于 `off`；它当前最确定的价值是控制主循环上下文和溢出风险。

**为什么摘要失败不影响回答？** 系统只接受产生净 Token 收益且结构合法的摘要。两次候选摘要没有缩短文本，因此被拒绝并保留原始消息，这是 fail-safe，不是信息丢失。

**Cross-Encoder 为什么只做重排？** 它把 query 与每个候选联合编码，相关性更精确，但计算成本随候选数增长；先用双塔/FAISS 召回小候选集，再做精排更经济。

**平台如何“购物”？** 它提供知识洞察、商品检索、偏好过滤、到手价估算和订单意向，不直接访问真实库存或支付接口。面试中应说“辅助购物决策”，不能说“完成购买”。

## 可以写与不能写

可以写：受控实验的加速比、Token 降幅、固定评测集指标、故障注入通过数、E2E 通过数，以及抽样 Trace 的实际完整数量。

不能写：真实 Prompt Cache 命中率、生产 QPS/SLO、线上转化率、全量遥测成功率、真实结账价格准确率、排障时间收益或完成真实支付。
