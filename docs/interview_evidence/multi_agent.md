# ORCH-001：多 Agent 与 Task DAG

## 实现链路

主 Agent 可直接调用商品/品类工具。只有任务可并行、需要上下文隔离或调用链预计达到三层之一成立时，路由策略才建议 fork。复杂任务先进入持久化 Task Board，依赖边决定 `runnable` 投影；派发在事务内完成校验和原子认领，随后使用 `asyncio.gather` settled 语义执行，成功和失败逐项幂等回写。认领同时写入 Worker 租约；Worker 中断后，下一次派发会回收过期租约并恢复为 `pending`，相同 Owner 对同一终态的网络重试是安全 no-op，不允许不同结果覆盖既有事实。

子 Agent 复用的是已编排的模型节点、工具节点、条件边、中间件和停止逻辑，不复用主 Agent 的消息 State。每个子任务生成独立 `thread_id` 和目录，但通过 `shopping_session_id` 继承同一购物会话身份。

## 确定性实验

每组运行 30 次：四路 I/O 串并行对照、菱形 DAG 解锁、单 Worker 失败、重复派发竞争、跨 scope canary、过期租约恢复和重复终态回写。门槛为 P50 加速比 ≥1.5、重复派发率 0、上下文泄漏率 0、成功结果保留率 100%、DAG 状态正确率 100%、中断恢复率 100%、幂等回写率 100%。原始结果写入 `orchestration.json`。

最新 offline 候选的 30 轮结果为：P50 串行 0.248 秒、并行 0.070 秒、加速比 3.55×；重复派发率和上下文泄漏率均为 0，DAG 正确率、部分失败保留率、中断恢复率和幂等回写率均为 100%。该结果运行于脏工作区，只能作为候选；正式简历数字仍须引用干净 Commit 上的发布快照。

## STAR 话术

- S：复杂购物请求在单循环中会造成上下文串扰，独立检索又可以并行。
- T：在不扩大子 Agent 权限的前提下提高吞吐，并支持失败隔离和恢复。
- A：将计划外置为依赖 DAG，使用原子认领、Worker 租约、隔离 thread、最小工具集和 settled 幂等回写。
- R：只引用 `orchestration.json` 的 P50/P95、加速比、泄漏率和重复派发率；真实模型规划质量另由 12 条 Kimi 场景评测。

## 取舍

没有给任务资源互斥锁建模，因此两个业务上冲突但数据依赖独立的任务仍可能被同时派发。它是已知限制，不把 DAG 正确性扩大为完整工作流引擎能力。
